> 版本 v2 · 2026-09-29
> v2 变更：范围定为**全量数据**、终态定为**刷题 Web 端**，新增 §8 产品架构、§9 改为双轨路线图、§12 决策状态

## 0. 结论先行

这份数据集的价值密度很高，但有两个**必须先解决的结构性问题**，它们决定了整个项目的架构：

**① 58,890 道题里只有 27,449 道是"新"的（重复率 53.4%）。**
所有下游处理（AI 标注、嵌入、聚合、统计）都必须建立在**去重后的题目实体**上，而不是原始题块上。做错这一步，工作量翻倍、成本翻倍、聚合结果被重复内容污染。

**② 解析里的数学公式是图片，不是文本（33,309 张公式图，被引用 115,349 次）。**
这是 `蒸馏方法参考.md` 里"资料分析疑点率 28.4%"的根因。不把公式还原成文本，数量关系和资料分析的解析对模型就是一堆 `[图片]` 占位符。这一层必须在蒸馏之前修好，否则要重跑。

**③ 数据集覆盖 516 套卷，国考只占 27 套（8%）。**
既然定为全量，国考/省考/选调/市考就作为**一等过滤维度**存在（`exam_type`），产品侧既能只刷国考，也能用省考题补充考点样本。注意这带来一个统计口径要求：**任何"频率/趋势"报表都必须标明统计范围**，否则国考与省考混算会得出无意义的结论。

在这三条之上，方向已明确：

> **全量数据（516 卷 / 27,449 唯一题） + 刷题 Web 端**
> 路线：Go 单二进制 + SQLite 起步的数据管线（解析入湖 → 去重实体化 → 公式还原 → LLM 蒸馏 → 质检 → 考点聚合），
> 之上叠 Web 服务层（题库检索、做题判分、错题本）与四类 AI 能力（智能解析、智能问答、智能推荐、智能出题）。

**关键排期洞察：首版 Web 端不需要 AI 就能上线。**
做题、判分、错题本、真题检索只依赖 P0–P2 的结构化题库，**不依赖蒸馏**。AI 能力才依赖蒸馏产物。因此数据管线（长跑批处理）与 Web 端（可先行交付）应当**双轨并行**，而不是串行等蒸馏跑完。

全量唯一题 27,449 道，按实测均价估算蒸馏成本约 **$18–30、约 18 小时**（并发 5）。

## 1. 数据现状（实测，非估计）

### 1.1 规模与版式

| 项目 | 实测值 |
|---|---|
| 卷（唯一试卷名） | 516 套，2016–2026 |
| 题块（原始） | 58,890 |
| **唯一题目实体** | **27,449**（题干+选项去重） |
| 唯一 `qid` | 27,473 |
| Markdown 文件 | 2,957 篇（模块卷）+ 6 篇模块索引 |
| 图片 | 39,461 张 / 367MB |
| 答案覆盖率 | 58,890 / 58,890 = **100%** |
| 官方解析覆盖率 | 58,890 / 58,890 = **100%** |

两种版式并存，解析器必须同时支持：

```markdown
## 第 1 题　<sub>qid 19283724 · 毛中特</sub>     ← 版式 A：独立题（43,904 道）
<题干 HTML>
- **A**. 选项　✅
**答案**：B
**官方解析**
<解析 HTML>

## 材料 1                                      ← 版式 B：材料组题（14,986 道）
<材料 HTML，含图表图片>
### 第 1 题　<sub>qid 4639483 · 综合</sub>       ← 挂在材料下
```

材料组题 14,986 道挂在 2,049 个 `## 材料` 段落下（资料分析、言语篇章、判断推理的材料题）。

### 1.3 数据质量体检结果

| 检查项 | 结果 | 结论 |
|---|---|---|
| `✅` 标记 vs `**答案**` 字段 | **0 处不一致** | 双信号可交叉校验，可作解析自检 |
| 4 选项 | 58,737（99.7%） | 主流形态 |
| 8 选项 / 5 选项 | 40 / 2 | 边界案例，解析器要容错不崩溃 |
| 判断题占位（`- （选项）[]`） | 111 | 107 道判定为 `judge`（答案 A/B 表示 正确/错误）；4 道答案标注为缺失，归入 `other`。**111 = 107 + 4** |
| 多选/组合答案（ABCD 类） | 405 | 判分要支持多选；实测多选会给**所有**正确项打 ✅ |
| 图片缺失 | 2 张 | 可忽略 |
| 图片体积 | 95% < 10KB | **公式图 OCR 成本极低** |

### 1.4 现有标签的局限

题目头部已带一个粗标签（`· 毛中特`、`· 增长`），共 23 个取值，但**不可直接用作考点**：

```
综合 4089 (27%)  ← 兜底垃圾标签，无信息量
增长 2238   片段阅读 1812   逻辑填空 1068   比重 1024   平均数 733
图形推理 572  类比推理 566  人文常识 525   逻辑判断 496   定义判断 484
数学运算 445  语句表达 387  法律常识 188   新思想 119   ...
```

`综合` 占了 27%，说明这层标签只到"二级题型"粒度，且存在兜底。**三级考点必须靠蒸馏产出**——这正是本项目存在的意义。

### 1.5 重复情况（决定工作量）

| 模块 | 题块 | 唯一题 | 重复率 |
|---|---:|---:|---:|
| 政治理论 | 2,305 | 1,084 | 53.0% |
| 常识判断 | 9,163 | 4,848 | 47.1% |
| 言语理解与表达 | 16,000 | 6,956 | 56.5% |
| 数量关系 | 6,448 | 3,223 | 50.0% |
| 判断推理 | 16,859 | 7,742 | 54.1% |
| 资料分析 | 8,115 | 3,595 | 55.7% |
| **合计** | **58,890** | **27,449** | **53.4%** |

两个关键推论：

1. **`qid` 与内容指纹互为验证，且指纹是"绝不拆分"的保守口径**。入库后实测交叉校验（`gk stats` 会打印）：

   | 方向 | 含义 | 实测 |
   |---|---|---:|
   | 一个 qid 被拆成多道实体 | 过度切分 → 同一道题会被重复蒸馏、白花钱 | **0** |
   | 一个指纹覆盖多个 qid | 过度合并 → 把源题库认为不同的题当成同一道 | **24** |

   唯一 qid 27,473 − 合并 24 = 27,449 = 题目实体数，账对得上。那 24 例是**唯一需要人工复核的去重裁决队列**，`gk stats` 会逐条列出（例如"2021年7月份，全国发电量大约是多少亿千瓦时？"在题库里有两个 qid）。
2. **重复是跨省联考造成的**（同一道题在 2016 联考河北卷、2017 广西卷都出现）。这不是脏数据，而是**有价值的关系**——"某考点在 11 个省份重复考过"本身就是高频信号。所以**不能删除，要做"题实体 ↔ 题目出现"的拆分**。

## 2. 项目定位

### 2.1 考试范围：**已定 = 全量**（国考/省考/选调/市考）

| 范围 | 卷数 | 唯一题 | 蒸馏成本 | 蒸馏耗时 |
|---|---:|---:|---:|---:|
| 仅国考 | 27 | 2,179 | ~$1.5 | ~1.5h |
| **国考 + 省考（全量）· 已选定** | **516** | **27,449** | **~$20** | **~18h** |

选择全量的技术理由（不只是"数据多"）：

1. **考点体系需要样本量才能收敛。** 2,179 道国考题摊到 6 个模块、几百个考点上，平均每考点不到 20 道——不足以支撑"高频考点统计"和"掌握度评估"。27,449 道才能让每个考点有足够实例。
2. **真题跨省重复是考点同源的证据。** 53.4% 的重复率说明各省命题高度共享考点，省考题在**考点层面**与国考同源，用作实例补充是合理的。
3. **横向对比是差异化功能。** "同一考点在国考和某省考分别怎么考"是纯刷题产品给不出的能力。

由此产生一条**产品侧硬性要求**：`exam_type`（国考/省考/选调/市考）与 `paper_variant`（副省级/地市级/行政执法/A类/B类/C类）必须作为一等过滤维度贯穿题库、检索、组卷、统计。**任何频率或趋势报表都必须携带统计范围**，国考与省考混算会得出无意义的结论。

### 2.2 产品功能架构（刷题 Web 端）

```
刷题 Web 端
├─ 题库浏览与检索
│   ├─ 按 年份 / 地区 / 考试类型 / 卷型 / 模块 / 卷 筛选
│   ├─ 关键词检索（SQLite FTS5）
│   └─ 语义检索（向量）＋ 按考点检索
├─ 做题
│   ├─ 单题练习（按考点 / 模块 / 随机）
│   ├─ 整卷模考（计时、作答、交卷、判分）
│   ├─ 按考点组卷 / 按错题组卷
│   └─ 错题重做
├─ 学习资产
│   ├─ 错题本（自动收集 + 手动收藏）
│   ├─ 做题记录、正确率、耗时统计
│   ├─ 考点掌握度（由做题表现反推）
│   └─ 笔记（挂在题上或考点上）
├─ AI 能力（四类，见 8.3）
│   ├─ 智能解析 · 学员视角逐题讲解
│   ├─ 智能问答 · 考点级对话 + 引用溯源
│   ├─ 智能推荐 · 基于薄弱考点的练习推荐
│   └─ 智能出题 · 按考点生成变体题
└─ 个人
    ├─ 账号与登录
    └─ 学习记录与数据导出
```

### 2.3 依赖关系：首版 Web 端**不需要 AI**

这是排期的关键。把功能按"是否依赖蒸馏产物"切开：

| 功能 | 依赖 P0–P2 结构化题库 | 依赖 P3–P5 蒸馏产物 |
|---|:---:|:---:|
| 题库浏览、筛选、关键词检索 | ✅ | — |
| 做题、判分、交卷 | ✅ | — |
| 错题本、做题记录、正确率统计 | ✅ | — |
| 组卷（按年份/地区/模块/卷） | ✅ | — |
| 按考点检索 / 按考点组卷 | — | ✅ |
| 考点掌握度、智能推荐 | — | ✅ |
| 智能解析、智能问答 | — | ✅ |
| 智能出题 | — | ✅ |

**结论**：上表前 4 行构成一个**可独立交付的 MVP 刷题站**，只需 P0–P2。AI 能力是增量叠加，不是首版前置条件。

因此路线图改为**双轨并行**（§9）：数据管线是长跑批处理；Web 端在 P0–P2 完成后即可开始，不必等 18 小时的蒸馏跑完。

## 4. 技术选型

| 领域 | 选择 | 理由 |
|---|---|---|
| 语言 | Go 1.26 | 已就绪；管线型任务 + 高并发 IO 是 Go 强项 |
| 存储 | **SQLite**（`modernc.org/sqlite`，纯 Go） | 816MB 数据集对数据库而言很小；纯 Go 免 CGO，交叉编译友好；WAL 支持并发读 |
| 全文检索 | SQLite **FTS5** | 与主库同源，无需额外服务 |
| 向量检索 | **内存暴力余弦**（不引向量库） | 27k × 768维 × 4B ≈ 84MB，单次全量比对 ~10ms 量级，向量库是过度设计 |
| Markdown 解析 | 自写**行扫描状态机** + `golang.org/x/net/html` | 格式高度规整（标题/选项/答案/解析固定行首标记），AST 解析收益低；题干内嵌 HTML 片段必须用 html 包 |
| Frontmatter | `gopkg.in/yaml.v3` | 标准选择 |
| LLM 客户端 | **自写 OpenAI 兼容 HTTP 客户端**（约 200 行） | 不锁 SDK；网关/多端点切换（参考文档 §3.7 提到同家网关有多套模型目录） |
| 并发 | `golang.org/x/sync/errgroup` + `semaphore` | 标准组合，实测并发 5 稳定 |
| CLI | 子命令式单二进制（`spf13/cobra` 或手写 `flag`） | 一个二进制覆盖全流程 |
| 日志 | `log/slog`（stdlib） | **写日志失败必须降级不上抛**（§3.5） |
| 测试 | 表驱动 + golden file | 解析器用 golden 保住 58,890 的解析契约 |

**关于"要不要用 Python"**：不需要。本项目没有训练任务，LLM 调用只是 HTTP，公式 OCR 可以走视觉 API 或独立小工具，Go 全栈可行且部署简单（单二进制）。

> 服务层（HTTP/前端/SSE/鉴权）的选型见 §8.1，本节只列数据管线的技术选型。

## 6. 核心设计

### 6.1 领域模型：题实体 vs 题目出现（L2 的关键）

这是整个数据层最重要的一个设计。直接后果是全量蒸馏成本减半。

```
question（题目实体，唯一，27,449 条）
├── id            自增主键
├── content_hash  归一化(题干+选项) 的哈希 ← 天然去重键
├── qid           原始题库 id（交叉校验 + 溯源）
├── module        模块
├── material_id   所属材料(可空)
├── stem          题干纯文本（图片→占位符）
├── stem_html     原始 HTML（保真备份）
├── has_figure    是否含题目图 ← 决定要不要走多模态
└── canonical_occurrence_id  代表题（取最早年份/国考优先）

question_occurrence（题目出现，58,890 条）
├── id
├── question_id   → question
├── paper_id      → paper
├── number        卷内题号
├── raw_qid       文件里的原始 qid
├── raw_tag       文件里的粗标签(如 `· 增长`)
└── in_material   bool

paper（卷，516 条）
├── id, name, region, year, module, question_count
├── exam_type     考试类型  ← 国考/省考/选调/市考，可过滤维度
└── paper_variant 卷型      ← 副省级/地市级/行政执法/A类/B类/C类
```

- `option`、`answer`、`explanation` 挂在 `question` 上（重复出现的内容一致，实测无冲突）。
- 指纹口径经实测选定为「题干+选项」，**不含材料正文、不去标点**，依据见 §6.2。
- **收益**：省考与国考共享的题只蒸馏一次；同时"这道题在 N 个省考过"成为可查询的高频信号。

### 6.2 解析契约（L1）

解析器是一切的根基，必须**可证伪**。`gk stats` 末尾会打印契约校验，任何一条对不上就说明解析坏了，下游全部不可信。

**已实现并验证通过**（`internal/store.CheckContract` 与 `internal/ingest` 的测试双重断言）：

| 校验项 | 实测 | 期望 | 类型 |
|---|---:|---:|---|
| 题块总数（occurrence） | 58,890 | 58,890 | 硬失败 |
| 题目实体（去重后） | 27,449 | 27,449 | 硬失败 |
| `✅` 标记 与 `**答案**` 字段冲突 | 0 | 0 | 硬失败 |
| 判断题（`judge`） | 107 | 107 | 硬失败 |
| 答案缺失 | 4 | 4 | 硬失败 |
| 被拆分的 qid（过度切分） | 0 | 0 | 硬失败 |
| 合并裁决队列（过度合并） | 24 | 24 | 报告项，进人工复核 |

同步产出：

- `option` 表：标签 / 内容 / 是否正确。正确性有**双信号**：选项行尾的 `✅` 标记 + `**答案**` 字段。全量实测两者 100% 一致（0 冲突），所以这个交叉校验是极灵敏的解析回归信号。
- `parse_warning` 表：42 道选项数异常（40 道 8 选项 + 2 道 5 选项）、4 道答案缺失。
- 答案类型判定：单选 / 多选（405 处）/ 判断（107）/ 其他（4）。

**一条被实测修正的预期**：不要期望 `option` 表有 `58,890 × 4 ≈ 235,000` 行。选项挂在**去重后的题目实体**上，所以实际是 `27,449 × 4` 减去判断题、加上 8 选项增量 ≈ **109,513** 行。若按"出现"存选项，同一道题的四组选项会重复存 27 次。

**必须处理的版式陷阱**（都是实测踩出来的）：

| 陷阱 | 现象 | 处理 |
|---|---|---|
| **全角空格** | 标题里题号与 `<sub>` 之间是 U+3000，而 Go 正则的 `\s` **不匹配**它 | 所有分隔处写 `[\s\x{3000}]`，不能用 `\s+` |
| **两种版式** | `## 第 N 题`（独立题，43,904 个）与 `### 第 N 题`（材料下，14,986 个） | 二级标题的题不隶属材料，且标志上一个材料段结束 |
| **判断题** | 111 道题用 `- （选项）[]` 占位，无真实选项 | 归入 `judge`，答案 A/B 表示 正确/错误；前端必须以「正确/错误」渲染 |
| **选项可超出 A–D** | 陕西省考有 8 个选项（A–H），答案是 H | 判分与渲染都不能按 A–D 写死 |
| **多选题的 ✅** | 多选会给**所有**正确项打 ✅（已在真实数据中确认） | 交叉校验按「标注集合 == 答案字母集合」比对 |
| **`---` 分隔符** | 材料下的多道题正是用 `---` 分隔 | 它结束当前题，但**不能**清空材料上下文，否则材料下第 2 题起会丢失材料归属 |
| **选项恒为单行** | 实测 0 例续行 | 若出现续行必须报警，不能静默吞掉——那意味着版式变了 |

**图片处理规则**：解析时把 `<img src="../90-图片/题目图/x.png">` **就地替换为占位符** `⟦IMG:题目图/x.png⟧`，而不是直接丢弃。理由：图片位置本身是语义信息（"下图中"、"根据上表"），模型看到占位符才知道此处有图；同时占位符是可逆的，便于 L3 回填公式。

另外要区分两种图：题面图（`has_figure`，实测 5,365 道，9.1%）决定蒸馏是否走多模态；材料图（`has_material_figure`）决定这道题能否只靠文本读懂——资料分析的材料图表不在题内，但缺了它题目就不可解。

**中文路径注意事项**：文件名含 `《》（）` 等全角字符，且有 2,957 篇 40+ 字符的长文件名。全程用 `os.ReadDir`/`filepath.WalkDir` 遍历，**不要拼接 shell 命令**，避免编码与转义问题。

### 6.2.1 去重口径：用 qid 当基准实测选出来的

去重键的定义不是拍脑袋定的，而是拿数据集自带的 `qid`（由原始题库分配，独立于我们的归一化策略）当基准，实测比对四种口径：

| 口径 | 唯一数 | 与唯一 qid(27,473) 之差 |
|---|---:|---:|
| **题干+选项** | **27,449** | **−24** ← 采用 |
| 题干+选项+材料 | 28,669 | +1,196 |
| 题干+选项+去标点 | 27,447 | −26 |
| 题干+选项+材料+去标点 | 28,668 | +1,195 |

两条结论都反直觉，值得记下来：

1. **不能把材料正文纳入指纹。** 资料分析看起来"必须带材料"，但同一道题在不同省份的材料排版（空白、HTML 实体）并不一致，纳入后会多切出 **4.4% 的伪新题**，直接把蒸馏成本抬高 4.4%。
2. **不需要去标点。** 去标点只多合并 2 道题，收益可忽略，却提高不同题被误判为同一道的风险。

最终口径（`ingest.ContentHash`）只取「题干 + 选项」，剔除所有空白与 `✅`，保留标点。该测试（`TestDedupDefinition`）保留在代码里，**任何人改归一化策略都会立刻看到口径偏移**。

入库后的交叉校验还给出一个更有用的结果——指纹是**"绝不拆分"的保守口径**：

| 方向 | 含义 | 实测 |
|---|---|---:|
| 一个 qid 被拆成多道实体 | 过度切分 → 同一道题会被重复蒸馏、白花钱 | **0** |
| 一个指纹覆盖多个 qid | 过度合并 → 把源题库认为不同的题当成同一道 | **24** |

账对得上：27,473 − 24 = 27,449。那 24 例是**唯一需要人工复核的去重裁决队列**，`gk stats` 会逐条列出（例如"2021年7月份，全国发电量大约是多少亿千瓦时？"在题库里有两个 qid）。因为过度切分会白花钱而过度合并只影响 24 道题，契约把前者设为硬失败、后者设为报告项。

### 6.3 考点规范表（L4 的核心资产）★

`蒸馏方法参考.md` §3.1 记录的最惨痛教训：**字段混用导致 11,282 道题产出 10,375 个三级考点**（几乎一题一标签，完全无法聚合）。根因是"考点名"和"这道题的具体做法"挤在同一个字段里。

架构上的应对是：**把规范表变成代码内的版本化资产，而不是 prompt 里的一段字符串。**

```yaml
# taxonomy/v1/03-verbal.yaml
module: 言语理解与表达
secondary:
  - name: 逻辑填空
    tertiary:
      - id: verbal.lk.01
        name: 实词辨析
        status: active          # active | pending | deprecated
        aliases: [实词辨析, 实词词义辨析]
      - id: verbal.lk.02
        name: 成语辨析
        status: active
  - name: 片段阅读
    tertiary:
      - id: verbal.pp.01
        name: 中心理解
        status: active
```

**规范表驱动 prompt 的三条硬约束**（均对应参考文档的实测坑）：

1. **prompt 由规范表程序化生成**，禁止手写枚举进 prompt。原因：§5 坑 1 记录"枚举示例会变成偏好名单，模型会把新考法压平成示例"。
2. **强制 `大类-` 前缀**，并在质检里做前缀校验。原因：§5 坑 2 "给了规范表，模型会漏前缀"。
3. **保留扩展口**：允许新增小类，但必须带前缀且与已有小类不重叠。原因：§5 坑 4，长尾 0.9% 经审查全是真实新考法。

**闭环**：规范表 → 生成 prompt → 蒸馏 → 校验（1:1 率、前缀合规）→ 新考点进 `pending` → 人工审查 → 升级 `active` → 规范表版本 +1 → 只对受影响批次重跑。

**字段设计（12 字段 + 疑点）**，直接沿用参考文档的结论：

| 字段 | 落库 | 设计要点 |
|---|---|---|
| 一级科目 / 二级题型 / 三级考点 | 独立列 | 三级考点=**纯考点名+前缀**，不带括号、不带本题做法 |
| 考点细节 | 独立列 | **与三级考点分离**，这是 1:1 率 92%→2.3% 的关键 |
| 问法模型 | text | 题干怎么问 → 用什么模型 |
| 推理链 | JSON 数组 | 3–8 步，每步必须引用题干具体数字/词句 |
| 最快解法 | text | 考场视角 |
| 易错点 | JSON 数组 | 1–3 条，将来做诱饵题的素材 |
| 母题抽象 | text | "当题干出现…特征时，用…方法，验证…" |
| 题干关键特征 | JSON 数组 | 3–6 个特征词，用于相似题匹配 |
| 适用边界 | text | **最容易漏的一段**，写具体误判场景 |
| 易混考点 | JSON | `[{考点, 区分信号}]` → 考点网络的"对比"边 |
| 典型提问 | JSON 数组 | 口语化，用于检索命中 |
| 疑点 | text | **安全阀**，模型与官方解析矛盾时只写这里，不动答案 |

### 6.4 LLM 蒸馏管线（L4）

**运行单元设计**：

```
var/runs/<run_id>/
├── manifest.json      # 配置快照：模型、prompt版本、规范表版本、题集hash、并发、时点
├── input.jsonl        # 本批题目清单（冻结，重跑时复用）
├── output.jsonl       # 逐题结果（追加写）
├── failures.jsonl     # 失败题 + 错误分类
└── run.log
```

**断点续跑**（对应 §3.4）：以 `output.jsonl` 中已完成的 `question_id` 集合为检查点。`input.jsonl` **冻结不复用抽样**，因为抽样脚本会排除已完成题，重跑时抽不回来。换输出目录 = 全量重跑，这正是"主动重跑某批"的正确手法。

**重试分级**（对应 §3.5）：

| 错误类型 | 处理 |
|---|---|
| 网络超时 / 5xx / 429 | 退避重试 |
| JSON 非法 / schema 不合规 | 重试（附带错误反馈，至多 2 次） |
| 内容越界（改答案、编造考点） | 重试 1 次，仍失败 → 记 `needs_review` |
| **结果写盘失败** | **不可重试**（重试=重复付费），落 failures 清单并告警 |
| 日志写入失败 | 降级为 stderr 告警，**绝不上抛** |

**溯源**（§3.7 / §3.10）：每条产出记录 `model_config_name` + `model_response_name`（API 回执里的模型名，不一致时告警）+ `prompt_version` + `taxonomy_version` + `tokens_in/out` + `cost` + `latency_ms`。混用来源的数据必须可过滤——参考文档明确说"不标记产地，下游质量口径会永久混在一起"。

#### 多模型并发（`gk distill run --models auto`）

动机很直接：配额若按模型记，N 个可用模型就是 N 倍吞吐。实测确实如此——同一时刻 `deepseek-flash` 返回 429 而 `deepseek-v4-flash` 成功，说明限流是分模型的。

**但按题轮流分给不同模型是错的。** 整个项目最难的一步是让考点收敛（参考文档最惨痛的事故是 11,282 题产出 10,375 个三级考点，完全无法聚合）。不同模型对同一考点的措辞天然不同——一个写「实词辨析」、另一个写「词语辨析」——混着跑只会让 1:1 率更差、聚合层被污染。参考文档 §3.10 对此有明确要求：混用来源必须标记产地，"否则下游质量口径会永久混在一起"。

所以切分以**「模块 × 题型」为不可拆分单元**，用最长处理时间优先（LPT）贪心装箱分配给各模型。这保证：

> **任何一个（模块 × 题型）单元内部的标注，始终出自同一个模型。**

粒度用数据自带的粗标签（逻辑填空 / 片段阅读 / 增长 …）而不是蒸馏产出的二级题型，因为粗标签在标注**之前**就存在，而二级题型正是待产出的东西——用未知的东西切已知的工作是切不动的。

实测负载均衡（22 个单元，总 27,445 题）：2 模型差 0.9%、3 模型 6.9%、4 模型 8.7%、6 模型 14.5%。`TestPartitionNeverSplitsABucket` 在各种分片数下断言上述不变量，`TestPartitionIsDeterministic` 保证同一输入给出同一分片（否则续跑会因切分变化而错位）。

落地要点：

- 每个执行器有**独立的客户端、并发度与退避**：一个模型被限流不会拖住其他执行器，这正是本方案相对单模型的价值
- 每个标注记录 `label.model`（v6 迁移），`label_run.engines` 记按模型聚合的用量，便于横向比较吞吐与质量
- **开工前的闸门**要求"至少一个模型可用"而非"全部可用"。多模型的价值恰恰是某个模型挂了别的能顶上；要求全部可用会让这套设计失去意义。全部不可用时按 `--wait-available` 等待并重探

#### 桶级动态领取 + 归属粘滞（最终形态，经 300 题实测）

最初实现是静态按题数均分（LPT 装箱），300 题验证跑暴露了它的缺陷：**它假设各模型吞吐相同**。实测 `deepseek-v4-flash` 只完成 48/102 时，另两个模型已跑完 96/99 和 90/99——慢模型成了整批的关键路径（预计拖长 45 分钟）。而配额状况随时间变化，事先测不准。

最终形态改成两层的组合：

1. **桶级动态领取**：桶（模块 × 题型，不可拆的最小单元）放进共享队列，大桶优先，谁空谁领下一个。快模型自然做得多，慢模型挂了队列自动流向健康模型。300 题实测：`sensenova-6.8-flash-lite` 最终领走 14/21 个桶，`glm-5.2` 3 个、`deepseek-v4-flash` 2 个——负载完全跟着实际吞吐走。
2. **归属粘滞**：领取时把「桶 → 模型」立即落盘（`bucket_owner.json`，先写临时文件再原子改名）。续跑时已归属的桶**回到原模型**，只有从未被领取过的桶才进队列。没有这层，中断续跑会让桶被两个模型各做一半，跨批次的"同一题型一个模型"不变量就破了。原归属模型不在本次列表时（如它被限流下线），桶重新分配并告警——桶内会出现两种模型的措辞，但 `label.model` 有记录可事后过滤。

**实测验证**（verify-300-dyn，同 300 题同种子）：

| 项 | 静态均分 | 动态领取 |
|---|---|---|
| 桶被拆开数 | 0/20 | **0/21**（不变量保持） |
| 题型内 1:1 率 | 24.8% | 28.1%（样本差异内一致） |
| 字段完备率 | 100% | 100% |
| 慢模型影响 | 关键路径 +45 分钟 | 无：队列流向健康模型 |
| 中断续跑 | — | 241 跳过 + 45 新做，粘滞归属正确恢复 |

动态领取不是对静态的优化，而是对**配额不稳定这个现实**的适应——这个端点上"各模型吞吐相同"从来就不成立。

#### 上游故障 ≠ 限流

实测遇到网关返回 `503 No available channel for model X under group Y`：这是上游渠道故障，不是"你请求太快"。两者混为一谈的后果很具体：

- 限流的正确反应是**退避几秒**再试
- 渠道故障的正确反应是**等分钟级**，因为上游真的挂了

若都按指数退避处理，重试次数会在几十秒内烧光，然后整批以失败告终——而真正该做的是等它恢复。因此 `llm.Error.Unavailable` 单独标记这类错误，退避直接用 60 秒；CLI 侧还有前置闸门避免在网关全挂时开工。

**答案铁律**（§3.9）：官方答案是唯一事实，模型不得改写；与官方解析矛盾只写 `疑点`。**疑点率是输入质量的报警器**，不是标注质量的负面指标。

### 6.5 多媒体处理（L3）

| 类型 | 数量 | 处理 | 说明 |
|---|---|---|---|
| **公式图** | 33,309 张（引用 115,349 次） | **本地 OCR → LaTeX，回填解析文本** | 中位尺寸仅 90×18 px；一次性投入，所有下游受益 |
| **题目图** | 6,152 张（5,365 道题，9.1%） | 标记 `has_figure`，蒸馏时走多模态 | 集中在判断推理 22.1%、数量关系 14.0% |

公式图是**必须做**的一层。不做的后果已经在参考文档里量化了：资料分析疑点率 28.4%，原因正是"材料图表转文字时丢失了公式图，模型靠复算绕过并如实上报"。

**已实现（P2）**：用 PaddleOCR 的 `PP-FormulaNet_plus-M`（GPU）批量识别，实测 8.3 张/秒，去重后 32,346 张约 65 分钟。产物写入 `image.ocr_tex`，再由 `gk media backfill` 把 `⟦IMG:公式图/x.png⟧` 替换进 `question.explanation_with_formula`。

三条落地经验（细节见 §9 P2）：

1. **`ocr_tex` 存原始输出，展示形态在回填时才算。** 分类判据属于展示层，改它只需重跑秒级的 backfill，不必重跑 65 分钟的 OCR。
2. **识别结果按 sha256 落盘、逐条 flush**，Go 侧每分片写库；worker 中途崩溃时已落盘部分仍会被采纳，重跑只补未完成的。
3. **用 CJK 当护栏决定要不要包 `$...$`**：含中文且无数学标记的是文字片段（"基期量"、"女研究生 > 男本科生"），包进 `$` 会让 KaTeX 用数学模式渲染汉字，比不包更糟。

题目图占 9.1%，两种策略可选：
- **A（推荐）**：这些题走多模态模型（传图 + 文本），其余题走纯文本。同一批次内按 `has_figure` 分流。
- B：题目图也 OCR 成文本（PP-OCRv5），统一纯文本管线。牺牲图形推理题（22% 需要看图找规律）的准确性。

> **已实现的中间选项（P2）**：资料分析的"材料图"多为表格与图表，**文字量很大**。对这批图跑一次文本 OCR（PP-OCRv5，6,152 张，约 15 分钟）显著改善了资料分析的可读性。实测效果——一张"2016年1-8月东中西部地区房地产开发投资情况"的表格图被还原成：
>
> ```
> 表1.2016年1-8月份东中西部地区房地产开发投资情况
> 投资额（亿元） | 同比增长率（%）
> 地区 | 住宅 | 住宅
> 全国总计 | 64387 | 43076 | 5.4 | 4.8
> 东部地区 | 35915 | 24188 | 5.4 | 3.9
> 中部地区 | 14078 | 9812 | 10.7 | 10.7
> ```
>
> 这些数据在纯文本版本里是完全丢失的。做法是**按 y 坐标把识别结果聚类成表格行**（行内按 x 排序、用 `|` 分隔）——若只是把文本按顺序平铺，行列关系就丢了，模型读到的是无法对齐的序列。图形推理的纯图形则提取不到文字，无害。

资料分析的材料图表要特别注意：图表在 `## 材料` 段落下，不在题内。解析时需把材料图片归属到该材料下的所有小题。

### 6.6 质检（L5）

**五个指标**（§6），每个都有坑，实现时按"坑"来写判据：

| 指标 | 判据实现要点 |
|---|---|
| 字段完备率 | 按模块分别统计，不只看全库平均 |
| 答案一致率 | **两层判据**：结论层（"答案为X"/"错误项为X"/"故选X"/"只有X项"）优先；弱判据（"X项正确"）仅兜底且加**否定守卫**（"故不选D"、"锁定A、C"、"B市"三类误报形态必须排除） |
| 三级考点 1:1 率 | 去重数/题数；>80% 说明字段混用。注意这是**收敛度**，不是正确性 |
| 疑点率 | **突然为 0 是危险信号**（安全阀没接上）；只与同模块基线比，不跨模块比 |
| 题型覆盖 | 单题型 ≥80% 时，结论不可外推 |

**抽样必须打散**（§3.2）：按类目轮转 + 固定种子随机，否则抽检样本会全落在最规整的题型上，得出偏乐观的结论。

**人工抽检不可省**（§3.11）：AI 审 AI 有自我偏好偏差，一致率高 ≠ 正确。抽检方式取"看推理链末步是否与官方答案一致 + 核对关键计算"，成本低且能抓住自动判据抓不住的问题。小样本必须报置信区间（16 题 0 错误只能说明错误率 <19%）。

CLI 层面提供一个 `gk review sample --run <id> --n 30` 产出 HTML 抽检页，回填结论入 `audit` 表。

### 6.7 考点聚合（L6）

从"每题一个标签"到"考点实体"：

1. **归一**：剥尾部括号与尾随破折号；**括号在中部时不剥**（那是考点名的一部分）。用**位置**判据，不用频次判据——低频不等于无效（§3.1）。
2. **实体化**：`concept(id, 名称, 模块, 二级, status, 是否晋级)` + `concept_alias` + `concept_question`（题→考点，多对多）。
3. **晋级门**（§3.12）：把**知识保留**和**可发现入口**解耦。
   - 三条必须全过：独立意图（会不会单独考它）、独立契约（有无独立问法模型+解法）、独立运行（不翻别的考点能不能讲完）
   - 再加至少一条：独立复用 / 独立评测
   - **未晋级的考点不删除**，挂在模块索引下仍可达
4. **关系图**：`concept_relation(源, 目标, 类型)`，类型为依赖 / 对比 / 组合。**对比边来自 `易混考点` 字段**，直接落成"考点辨析"。
5. **不追求 100%**：约 9.8% 无括号可拆、约 4.2% 跨多考点（集中在资料分析"综合"类），**保留原字符串，不强行合并**——强行合并比不合并更糟。

### 6.8 检索设计

检索是 Web 端与 AI 问答的共同底座，其中**"检索单元是题还是考点"是最关键的决策**（参考文档 §0 提出）：

> **推荐：以「考点卡」为主检索单元，真题作为引用证据。**
> 因为学习者问的是"增长量和增长率的区别"——这是**考点级**问题，不是"某一道题怎么做"。若以题为检索单元，会召回一堆题干相似但考点不同的题，答非所问。

三层检索：

| 层 | 实现 | 用途 |
|---|---|---|
| 关键词 | SQLite **FTS5**，索引 `题干 + 解析 + 考点名 + 典型提问` | 精确查找、题干片段搜索 |
| 语义 | 嵌入存 BLOB，Go 内存暴力余弦（27k × 768 ≈ 84MB，~10ms） | 自然语言提问、模糊回忆（"那个关于鬣狗的题"） |
| 结构化 | 按 `module / concept / exam_type / year` 过滤 | 组卷、按考点练习、统计 |

设计要点：`典型提问` 字段（蒸馏产出的第 12 个字段，口语化）**专为检索命中而生**——用户的口语提问与它做语义匹配，比与学术化的考点名匹配命中率高得多。这是蒸馏产出反哺检索的直接例子。

## 8. Web 产品架构

> 本节回答"终态是刷题 Web 端"带来的新增设计。§3–§7 的数据管线仍是地基，本节是叠在其上的服务层。

### 8.1 技术选型（服务层）

| 层 | 选型 | 理由 |
|---|---|---|
| HTTP 服务 | `net/http` + `chi` | 标准库够用；chi 轻量、无框架绑定 |
| 前端 | **Vue 3 + Vite**（已定，见 §12） | 刷题交互状态多（作答/计时/判分/错题），KaTeX 集成成熟 |
| 交付形态 | 前端构建产物用 **`embed.FS` 内嵌 → 仍是单二进制** | 保留 Go 部署简单的核心优势，不引入 Node 运行时 |
| 流式输出 | **SSE**（`http.Flusher`） | 智能问答/解析逐字输出，Go 原生支持良好 |
| 公式渲染 | **KaTeX** | 直接消费 L3 OCR 出的 LaTeX。**若不做 L3，前端只能回退显示公式图** —— 这是 L3 的第二个下游收益 |
| 鉴权 | 会话 Cookie + `argon2id` 密码哈希 | 简单起步，预留 OAuth/微信登录扩展点 |
| 静态图片 | `var/assets` 下导出 + `Cache-Control` 强缓存 | 39,461 张；可按 `sha256` 做 ETag |
| 向量检索 | 内存暴力余弦 | 27k × 768 维 ≈ 84MB，查询 ~10ms，**不引向量数据库** |
| 仓储层 | **接口化**（`Repository` interface） | 见 §8.6：离线管线用 SQLite，在线服务用 Postgres，两者靠发布步骤衔接 |

**关于前端的一处诚实提醒**：本项目所有数据与 AI 能力都在 Go 侧，前端只做交互与渲染。所以前端选型是**可替换的**——先用 Vue 3 起步，若后续想换成 React 或 Go 模板 + HTMX，改动只在前端目录，不影响后端。

### 8.2 API 设计

```
# 题库
GET  /api/papers?exam_type=&year=&region=&module=      # 卷列表
GET  /api/questions?module=&year=&concept=&page=       # 题目列表
GET  /api/questions/:id                                # 题目详情（★不含答案与解析）
GET  /api/questions/:id/answer                         # 提交作答后取答案与解析

# 做题
POST /api/practice/sessions                            # 开始一次练习（组卷，返回冻结题序）
GET  /api/practice/sessions/:id                        # 恢复会话
POST /api/practice/sessions/:id/submit                 # 交卷判分（服务端判分）
GET  /api/practice/records                             # 做题记录与统计

# 学习资产
GET  /api/wrongbook             POST /api/wrongbook    # 错题本
GET  /api/concepts/:id                                 # 考点卡（含关系、真题实例）
GET  /api/concepts/:id/questions                       # 考点下的真题

# 检索
GET  /api/search?q=&mode=keyword|semantic              # 关键词 / 语义检索

# AI
POST /api/ai/explain           (SSE)                   # 智能解析
POST /api/ai/chat              (SSE)                   # 智能问答
GET  /api/ai/recommend                                 # 智能推荐
POST /api/ai/generate-question                         # 智能出题（管理员）
```

**两条安全设计**：
1. **题目详情接口默认不下发答案。** 判分在服务端做（`/submit`），避免前端可拿到答案。
2. **AI 出题接口限管理员权限**，不在用户侧开放——生成题需要过质量门（§8.5），不能即时产即时用。

### 8.3 四类 AI 能力：技术路径与建设顺序

| 能力 | 技术路径 | 依赖蒸馏 | 缓存 | 顺序 |
|---|---|---|:---:|:---:|
| **智能解析** | 题 + 官方解析 + 考点标注 → 分层讲解：①官方解析原文 ②考点提炼 ③分步讲解（用`推理链`）④易错提醒（用`易错点`）⑤横向对比（用`易混考点`） | 强 | **按 question_id 落库** | ① |
| **智能推荐** | 错题 → 考点映射 → 薄弱/高频考点 → 推荐同考点真题。**初版可纯规则实现，不需要 LLM** | 强 | 实时计算 | ② |
| **智能问答** | 用户问题 → 向量检索（考点卡 + 真题）→ 组装上下文 → 流式生成 → **带引用**（引到具体考点/题号） | 强 | 可选语义缓存 | ③ |
| **智能出题** | 考点 + 难度 → 用 `母题抽象` 生成变体题 + 答案 + 解析 → **质量门** → 隔离入库 | 强 | 不缓存 | ④ |

**① 智能解析的缓存设计是成本模型的核心。**
解析是**确定性产出**——同一道题全站用户看到的一样。因此首次请求时生成并落库，之后直接读缓存：

```
全站 AI 解析成本 = 被访问过的题目数 × 单题成本      ← 不是 用户数 × 题目数
```

即使有 1 万用户，解析总成本上限仍是 `27,449 × $0.00065 ≈ $18`。"预生成 + 按题缓存"相对"每次现算"是决定性的成本优势，必须在设计阶段就定下来，事后改要用量数据迁移。

**② 智能推荐可先不接 LLM。** 规则版已经可用：错题 → 查 `concept_question` → 该考点下未做过的真题 → 按真题出现次数（跨省重复次数）排序推荐。**跨省重复次数是一个现成的、免费的难度/高频信号**——被 11 个省考过的考点显然比只考过 1 次的更重要。这条信号来自 P1 的 `question_occurrence` 表，零成本。

**③ 智能问答要解决"引用一致性"。** RAG 最容易翻车的地方是生成内容与检索到的证据脱节。设计要求：回答中每个结论都要能指回具体的 `concept_id` 或 `question_id`，前端把引用渲染成可点击的真题/考点卡。做不到引用就不要输出该结论。

**④ 智能出题放最后，因为最容易翻车。** 生成题质量不可控，必须过质量门（§8.5）。把它排在最后，前三个能力的产出（考点卡、易错点、母题抽象）恰好是它的输入——顺序是技术依赖倒推的，不是随意的。

### 8.4 应用层数据模型

补充 §7 数据层的新增表：

```sql
-- ============ 用户与做题 ============
CREATE TABLE app_user (
  id INTEGER PRIMARY KEY, username TEXT UNIQUE NOT NULL,
  password_hash TEXT, nickname TEXT,
  created_at TEXT, last_login_at TEXT
);

CREATE TABLE practice_session (                    -- 一次练习 / 模考
  id INTEGER PRIMARY KEY, user_id INTEGER REFERENCES app_user,
  kind TEXT,          -- single | paperset | concept | wrongbook
  spec TEXT,          -- JSON：组卷条件快照（保证可复现）
  question_ids TEXT,  -- JSON 数组：冻结的题序
  started_at TEXT, submitted_at TEXT,
  total INTEGER, correct INTEGER, duration_ms INTEGER
);

CREATE TABLE practice_answer (
  id INTEGER PRIMARY KEY,
  session_id INTEGER REFERENCES practice_session,
  question_id INTEGER REFERENCES question,          -- 引用题实体，不存副本
  ord INTEGER, user_answer TEXT, is_correct INTEGER,
  duration_ms INTEGER, answered_at TEXT,
  UNIQUE(session_id, ord)
);

CREATE TABLE wrongbook (
  user_id INTEGER, question_id INTEGER,
  source TEXT,        -- auto(判错自动收录) | manual(手动收藏)
  wrong_count INTEGER, last_wrong_at TEXT,
  resolved INTEGER,   -- 是否已订正
  PRIMARY KEY (user_id, question_id)
);

CREATE TABLE user_concept_stat (                   -- 考点掌握度（智能推荐的输入）
  user_id INTEGER, concept_id INTEGER,
  answered INTEGER, correct INTEGER,
  mastery REAL,       -- 0..1
  updated_at TEXT, PRIMARY KEY (user_id, concept_id)
);

CREATE TABLE note (
  id INTEGER PRIMARY KEY, user_id INTEGER,
  target_type TEXT,   -- question | concept
  target_id INTEGER, content TEXT, updated_at TEXT
);

-- ============ AI 运行时 ============
CREATE TABLE ai_explain_cache (                    -- 智能解析缓存（成本模型核心）
  question_id INTEGER PRIMARY KEY REFERENCES question,
  content TEXT,       -- JSON：分层讲解
  model TEXT, prompt_version TEXT,
  tokens_in INTEGER, tokens_out INTEGER, created_at TEXT
);

CREATE TABLE ai_chat_log (                         -- 问答日志（质检 + 语义缓存素材）
  id INTEGER PRIMARY KEY, user_id INTEGER,
  question TEXT, answer TEXT,
  citations TEXT,     -- JSON：[{type, id}] 引用溯源
  retrieved_ids TEXT, -- JSON：检索命中
  latency_ms INTEGER, created_at TEXT
);
```

**两处设计取舍**：

1. `practice_answer` 引用 `question_id` 而非拷题目副本。代价是题目被修正后历史作答的展示会变；收益是数据库不膨胀（否则每次练习都存一份题干）。折中方案：`practice_session.spec` + `question_ids` 冻结了**当时的题序与组卷条件**，已足够追溯"当时考的是哪套题"。
2. `user_concept_stat` 必须由做题记录**聚合**而来、可重算，**不要**把它当唯一真相源。真相源是 `practice_answer`；掌握度是派生视图。

### 8.5 AI 生成题的隔离与质量门

生成题**绝不能混入真题库**——会污染统计口径、考点聚合和"高频考点"结论。物理隔离：

```sql
CREATE TABLE generated_question (
  id INTEGER PRIMARY KEY,
  concept_id INTEGER REFERENCES concept, source_question_id INTEGER,
  difficulty TEXT, stem TEXT, options TEXT, answer TEXT, explanation TEXT,
  model TEXT, prompt_version TEXT, dedup_hash TEXT,
  quality_status TEXT,   -- pending → passed → rejected
  created_at TEXT
);
```

**准入质量门**（五项全过才可进入练习池）：

| # | 判据 | 实现 |
|---|---|---|
| 1 | 结构完整 | 题干 + 4 选项 + 答案 + 解析齐全 |
| 2 | 答案自洽 | 模型给的答案与其解析结论一致（复用 §6.6 两层判据） |
| 3 | 去重 | 与 27,449 道真题及其他生成题的哈希/高相似不重合 |
| 4 | 可解性 | **独立模型盲解**（只给题干不给答案），答案一致才通过 |
| 5 | 人工抽检 | 抽样审查，通过率作为生成 prompt 的评估指标 |

未通过的进 `rejected`：**保留但不参与练习**，作为改进生成 prompt 的素材（对应参考文档 §5 的"扩展口"思路——低质产出不是垃圾，是信号）。

### 8.6 部署架构（对外多用户）

已定：**对外多用户、需要上线部署**。这一条改变的不是"要不要换数据库"这么简单，而是**离线管线与在线服务必须解耦**。

#### 核心决策：离线管线继续用 SQLite，在线服务用 Postgres

不能"把整条管线搬到 Postgres"吗？可以，但没必要，而且代价被低估了。整条管线（解析、去重、OCR 回填、蒸馏、聚合）有强假设：

- **单写者**：一次 ingest 就是一次批量写，天然只有一个进程在写
- **单机**：33,309 张图片的 OCR、27,449 道题的蒸馏，都跑在一台机器上
- **可重放**：任何一层都可以从上层产物重跑，不需要高可用

Postgres 的价值（并发写、高可用、在线扩展）在这一侧**一个都用不上**，而移植成本是实打实的——现有 SQL 里有 `INSERT OR IGNORE`、`GROUP_CONCAT`、`?` 占位符、`MAX(a,b)` 等 SQLite 方言，全都要改，且改完就永久失去了"单文件数据库、`--reset` 重跑、随手拷贝一份排查"的便利。

在线侧则完全相反：多用户并发写做题记录、错题本、AI 缓存，SQLite 的单写者（WAL 模式下）会成为瓶颈，且无法水平扩展。

所以：

```
离线（单机批处理，可重放）              在线（多用户，水平扩）
┌────────────────────────────┐        ┌────────────────────────────┐
│ gk ingest / media / distill │        │  gk serve × N（无状态）      │
│        / aggregate          │        │        │                    │
│            ▼                │        │        ▼                    │
│   var/db/gk.sqlite          │───────►│   PostgreSQL 16             │
│   （题库 + 蒸馏产物，只读发布）│  gk    │   题库（只读）               │
└────────────────────────────┘ publish └────────────────────────────┘
              ▲                                  ▲
              │                                  │
       var/runs/（批次产物）              对象存储 / CDN（图片）
```

**`gk publish` 是两者之间唯一的桥**，它把 SQLite 里的题库与蒸馏产物发布成 Postgres 里一个**命名快照**。这个额外的一步换来两个真实收益：

1. **在线库不承载管线复杂度**：服务层永远只读题库，只管用户数据，职责干净
2. **题库可版本化回滚**：发布是幂等的、带版本号的操作。蒸馏跑坏了，回滚到上一个快照即可，而不是重新跑一遍 18 小时

#### 在线侧的关键约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | **`gk serve` 必须无状态** | 会话/缓存不能落本地磁盘，否则无法水平扩；多实例部署时也要能随时替换 |
| 2 | **题库表只读，用户数据读写** | 这条拆分决定了索引设计与扩容策略；题库可放只读副本 |
| 3 | **图片走对象存储/CDN，不走应用磁盘** | 39,461 张 / 367MB。文件名已经是 `formula-<16位hex>.png` 这种内容哈希形态，天然不可变 → 可下发 `Cache-Control: immutable` 长期缓存，回源压力接近零 |
| 4 | **AI 解析缓存在 Postgres，不在本地文件** | 缓存是成本模型的核心（§8.3①），多实例共享同一份缓存才有意义 |
| 5 | **管线不在线上服务器跑** | 18 小时的蒸馏跑在线上会挤占用户请求资源；应以离线 worker 产出快照再发布 |
| 6 | **限流与成本闸门** | AI 问答按用户限流，并有全局日预算上限——这是唯一会让成本随用户数线性增长的地方（§11 风险 12） |

#### 部署形态建议

| 阶段 | 形态 | 说明 |
|---|---|---|
| 首发 | **单机 + Docker Compose** | Nginx/Caddy（TLS + 静态缓存）+ `gk serve` + Postgres + 对象存储客户端。够撑到数千日活 |
| 扩容 | `gk serve` 多实例 + 托管 Postgres | 因为服务无状态，加实例即可；Postgres 换托管服务省运维 |
| 不推荐的首发选择 | Kubernetes | 单机 Compose 能解决的事，K8s 只会增加上线时间与故障面 |

**交付物仍是一个镜像**：前端 `dist/` 由 `embed.FS` 内嵌进 `gk serve`，加上 Postgres 连接串与环境变量即可运行。这是选 Go + 内嵌前端的主要回报——不需要为前端单独维护一套部署。

### 8.7 管理入口（已实现）

已定需要"管理入口，可自定义 API 地址、apikey 等内容"。这不是把配置从文件搬到数据库那么简单，有几条安全约束必须一起做，否则入口本身就是漏洞。

#### 形态

```
gk serve                        → http://<addr>/        前端（Vue 3，embed 内嵌）
                                  /admin                管理页面
                                  /api/admin/login      登录
                                  /api/admin/settings   读写配置（GET/PUT）
                                  /api/admin/test-llm   连通性测试
                                  /api/admin/password   改口令
```

CLI 侧保留等价能力，便于无头环境与 CI：`gk admin create/passwd`、`gk config list/set`。

#### 五条安全约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | **密钥加密后存库**（AES-256-GCM） | 明文存 API key 等于把凭据暴露给任何能读库的人。密钥来自 `GK_SECRET_KEY`，未设置时落一份 0600 的 `var/secret.key` 并提示备份 |
| 2 | **读取接口只返回掩码** | 用固定长度的 `••••••••`，不泄漏真实长度。避免密钥顺着某个"返回全部配置"的接口漏出去 |
| 3 | **提交掩码时保持原值** | 否则管理界面每次保存都会把遮蔽显示写回去，把真实 key 抹成字面量 `••••••••` |
| 4 | **管理员与用户体系分开** | 这是能改服务端配置的运维身份，权限远大于普通用户，不能共用账号表，也不允许自助注册 |
| 5 | **改口令吊销全部旧会话** | 改密码后旧会话继续有效是常见疏漏 |

#### 连通性测试要核对两件事

`/api/admin/test-llm` 不只验证"能不能通"，还**核对回执里的模型名与配置名是否一致**并给出告警。理由见 §6.4：配置名只能证明我们请求了什么，证明不了请求实际路由到了哪个模型；不一致会同时影响成本口径与质量口径，必须让人看见。

#### 登录失败不做区分

用户名不存在与口令错误返回同一句话，且对不存在的账号也走一次 bcrypt 比较以抹平耗时差——避免账号枚举。

### 8.8 仓储层接口化的具体边界

为了让上面的拆分成立，**SQL 不能泄漏到业务层**。需要划出的边界：

```
internal/store        ← 唯一允许出现 SQL 的地方
  sqlite/             ← 离线管线实现（现有）
  postgres/           ← 在线服务实现（P6 前完成）
internal/practice     ← 只调用 Repository 接口，不认识数据库
internal/ai
internal/serve
```

接口按用途拆开，不要一个巨型 `Store`：

- `QuestionRepo`（只读）：按模块/考点/年份取题、组卷、检索
- `PracticeRepo`（读写）：会话、作答、错题本、统计
- `AIRepo`（读写）：解析缓存、问答日志、成本记账
- `ConceptRepo`（只读）：考点卡与关系

**离线侧不需要接口化**（它就是 SQLite，没有第二个实现），只有在线侧需要。把接口加在离线管线里是纯粹的空转。

### P2 · 公式还原 ✅ 已完成
```bash
gk media index                                  # 图片一致性同步 + sha256 + 尺寸
gk media ocr-formula --shard 11000 --batch 24   # 公式图 → LaTeX（PP-FormulaNet）
gk media ocr-text    --shard 3000  --batch 8    # 题目图 → 表格文本（PP-OCRv5）
gk media backfill                               # 占位符 → 文本，写入三处派生列
gk media report                                 # 覆盖率与残留率
gk media sample --n 30                          # 分层抽样人工核对
```
- 交付：`internal/media` + `tools/ocr_{common,formula,text}.py`；`image` 表补齐 sha256/尺寸/OCR 结果与引擎，`question.explanation_with_formula` / `stem_with_text` / `material.body_with_text` 落库

**实测结果**（GPU GTX 1660 Ti）：

| 指标 | 结果 |
|---|---|
| 公式图 | 33,309 张识别，**0 失败**，8.3 张/秒 ≈ 66 分钟 |
| 题目图 | 6,152 张识别，**0 失败**，11.5 张/秒 ≈ 15 分钟 |
| 公式占位符 | 替换 54,821 处，**残留率 0.0%**（验收线 <5%） |
| 材料/题面 | 已还原材料 1,570/1,570、题面 3,548/3,548，**真正的缺口 0** |
| 唯一未还原项 | 仅 2 处——磁盘上物理缺失的 2 张图（`图片缺失清单.txt` 记录在案） |

- **三处设计要点**：
  1. **`ocr_tex` 存原始输出，展示形态在回填时才算**。分类判据用真实输出定标并锁进测试，改判据只需重跑秒级的 backfill，不必重跑 66 分钟的 OCR
  2. **三处派生列执行同一条规则**：所有能提取内容的占位符都替换，只有确实提取不到文字的图才保留占位符（前端据此渲染 `<img>`，蒸馏模型据此知道此处有图）。**不给某类图开特例**——早期版本只让材料解析题面图，材料正文里的公式图一直残留，而资料分析的数据恰恰全在材料里
  3. **用 CJK 当护栏决定要不要包 `$...$`**：含中文且无数学标记的是文字片段（"基期量"、"女研究生 > 男本科生"），包进 `$` 会让 KaTeX 用数学模式渲染汉字，比不包更糟；定界符内侧的空白也要去掉，否则 auto-render 可能不识别

- **过程中发现并修掉的三个 bug（都是静默的）**——这一段比结果更有参考价值：

  | # | bug | 表现 | 修法 |
  |---|---|---|---|
  | 1 | **`zip(chunk, predict(paths))` 错位** | predict 静默跳过不支持的文件，返回列表比输入短；zip 于是把后续每张图的文本挂到**前一张**的 sha256 上。5,211 张里 11 张无记录、最多数千条可能错配 | worker 改按索引配对；长度不匹配时逐张重跑；Go 侧再加一道"期望条数 vs 实际条数"校验 |
  | 2 | **材料图片没登记进 `image` 表** | ingest 只登记了题干与选项的图，材料正文引用的 1,140 张（843 题目图 + 297 公式图）没有行、没有 sha256、拿不到 OCR → **材料表格回填率 0%** | ingest 补登记材料图；并加 `Reconcile` 从"引用口"反向补全（扫遍所有可能出现占位符的文本列），幂等且不动已有 OCR 结果 |
  | 3 | **不支持的格式被静默跳过** | 数据集中有 7 个 `.gif` + 4 个 `.jfif`，PaddleOCR 不支持这些后缀，只往 stderr 打一行警告就被跳过 | 识别不到结果且后缀不在支持列表时，用 PIL 转 PNG 重试（图片本身是好的） |

  **一条被推翻的旧结论**：P0 阶段 `gk media index` 报的"孤儿图片 1,140 张（无任何引用）"是**误读**——它们不是孤儿，而是被材料正文引用、但 ingest 漏登记的图片。修好登记后孤儿数变为 **0**。教训是：一个指标异常时，先怀疑产生它的那条链路，而不是接受它的字面含义（对应参考文档 §3.6"读到反常结果时先怀疑自己的读取代码"）。

- **价值**：消除参考文档中"资料分析疑点率 28.4%"的根因；前端 KaTeX 渲染直接依赖这一层

```bash
gk distill report                           # 五个质检指标
```
- 交付：`taxonomy/v1/taxonomy.yaml`（规范表）+ `internal/distill`（prompt/schema/runner）+ `internal/llm`（OpenAI 兼容客户端）
- 验收：**1:1 率 <10%**（考点收敛）、前缀合规 100%、答案一致率 100%、人工看完 50 条
- **价值**：50 题足够暴露字段设计和 prompt 的大部分问题（参考文档的 92% 标签爆炸、选非误报、题型覆盖偏差全都在这 50 题里就能看出来），成本只有几美分
- **如果这一步的字段设计需要改，现在改，成本几美分；全量跑完再改，成本 18 小时**

**已落地的三处结构性设计**：

1. **提示词由规范表程序化生成**（`BuildSystemPrompt`），不手写枚举。手写会让模型把示例当"偏好名单"，遇到新考法就往示例上压平（§5 坑 1）；给了规范表又会漏「大类-」前缀（坑 2），所以 `ValidateTertiary` 强制校验前缀必须等于二级题型名。
2. **"答案不可改"是结构约束，不是提示词自律**：产出里**根本没有答案字段**，模型无从改写；额外要一个 `conclusion`（它自己的判断），与官方答案的差异只用于统计"答案一致率"。这比"请勿修改答案"这条规则更硬。
3. **断点续跑以 `label(question_id, run_id)` 唯一约束为准**，产物同时落 `output.jsonl` 与 `failures.jsonl`：盘上是审计凭据，库是查询入口。失败清单区分可重试/不可重试（§3.5），本轮实测把 401 正确判为不可重试、零浪费重试。

#### 规范表 v1.3：50 题 MVP 驱动的修订（含验证）

P3 的价值不在于跑出多少标注，而在于**用实测改进规范表**。MVP 一轮就暴露了三处问题，逐条修订并用同一批 50 题回跑验证：

| # | 发现（实测依据） | 修订 | 验证结果 |
|---|---|---|---|
| 1 | **「新思想」分档维度选错**：原按主题领域分（以人民为中心 / 中国式现代化…），但实测这些主题词全库只命中 138 题，而「新思想」标签下有 1,419 题。抽查发现主体是**某次会议/讲话/报告里的具体提法**（政治理论内：会议 133 / 大会 102 / 讲话 75 / 报告指出 63 / 全会 58），这些题原先无处可去 | 补 `新思想-重要论述与讲话精神`、`新思想-理论定位与核心内容` | 新思想从 **3 题→3 考点**（1:1）变为 **5 题→1 考点** |
| 2 | **党章/党的组织制度无处可去**（实测 68 题：党章 14 / 党员 33 / 中央委员会 17 / 党的组织 4 / 党的纪律 3），只能挤进「新思想」，而党章与习近平思想不是同一层概念 | 新增二级题型 `党章党规`（4 个三级考点） | 已被命中；也修正了那句「新思想占 27% 是兜底标签」的隐患 |
| 3 | **「公务员制度」被标进人文常识**（模型跟着源标签走，源标签确实写的人文常识）。但全库「公务员法」31 题、「公务员制度」3 题本是同一主题，按原分档会被拆到法律常识与人文常识两处 | 补 `法律常识-公务员制度与公务员法`；加"现代制度→法律常识、古代制度→人文常识"的时代边界规则 | 该批样本未命中（标注它的模型配额耗尽），待下一批确认 |

同时补了两条**归类边界**（参考文档 §5 坑 5：边界不写死，模型就会在边界上摇摆）：

- **「讲话」归属**：考思想性提法（"六个必须坚持""四个伟大成就"、报告对某规律的论断）→ `新思想-重要论述与讲话精神`；考时政事实（会议何时何地、政策数字）→ `时事政治`。同一场讲话按**考什么**分，不按讲话本身分。修订前 `时事政治-重要讲话` 与模型自造的 `新思想-重要讲话` 在打架，模型只能猜。
- **制度类常识按时代分**：现行法律法规确立的现代制度 → `法律常识`；古代与历史制度（科举制、三省六部制）→ `人文常识-历史事件`。

**验证结果**（同一批 50 题、同种子、仅换规范表）：

| 指标 | v1.2 | v1.3 |
|---|---|---|
| 题数>1 的题型内 1:1 率 | 74.3% | **59.4%** |
| **规范表外新增考点** | **2 个** | **0 个** |
| 字段完备率 | 100% | 100% |

最后一行是最干净的证据：修订前模型**不得不自己发明**两个考点（因为规范表缺槽位），修订后一个都不用发明——说明规范表已覆盖题目的实际空间。

#### 扩量验证：300 题暴露了 v1.3 的过度矫正（v1.4）

50 题的信号太弱。按建议扩到 300 题（同一批种子、分层打散）后，两件事同时发生：

**一、1:1 率从 59.4% 降到 26.3%**（232 题 → 61 考点，平均 3.8 题/考点）。之前的数字是失真的——50 题摊在 17 个题型上，其中 6 个题型只有 1 题，必然"一题一考点"。**判断 1:1 率至少要 200 题以上**，否则量的是抽样设计而不是规范表质量。

**二、v1.3 对「新思想」的修法过度矫正。** 我当时只补了一个宽槽位「重要论述与讲话精神」，300 题跑出来 **27 道新思想题全落进它**。27:1 的收敛度看着漂亮，但抽查这 27 题的领域横跨外交、党史、文化、治疆、十五五规划、乡村振兴、粮食安全——**它是个筐，不是考点**，学习者看到它得不到任何信息。

根因是领域分档太窄（只有 5 个），逼模型把一切塞进最接近的宽槽位。按实测题量补 11 个领域考点后（v1.4，118 个三级考点），验证结果：新思想 **1 个考点 → 11 个**，平均 4.6 题/考点。

> **两个容易踩的解读陷阱**（都在这轮踩到）：
>
> 1. **"收敛度"可以被做假。** 把槽位做粗就能让 1:1 率变漂亮。所以这个指标必须配合"每题考点数"与"抽查槽位内的题是否真属同类"一起看。我在 v1.3 就差点用漂亮的数字掩盖了一个筐。
> 2. **疑点率是模型特异信号，不能跨模型比。** 实测 deepseek-v4-flash 16%、glm-5.2 12%、sensenova-6.8-flash-lite 7%。而"言语理解疑点率 0%"是假象——该模块 49 题**全部由 sensenova 标注**。跨模型跑批时疑点率必须按模型分组看，否则会把模型特征读成模块特征。

**一条方法论**：修订规范表要**先查数据再动手**。上面每一条都写明了实测题量。中途我还查过「古代制度」类题目，发现只有 3 题，于是**决定不为它加分档**——凭想象扩展规范表会把分档做虚。

**一处与参考文档不同的做法**：参考文档的产出没有 `conclusion` 字段，其"答案一致率"靠从解析里启发式抽取结论（因此有两层判据与四种误报形态，§3.3）。本项目改为**让模型显式输出它自己的判断**，把启发式抽取换成结构化字段——误报源从"文本判据"变成了"模型是否听话"，判据简单得多。

| 10 | **SQLite 并发写瓶颈** | Web 端多用户写做题记录时阻塞（WAL 单写者） | 起步可行（题库读多写少）；仓储层接口化，预留 Postgres 切换；写路径批量事务、避免长事务 |
