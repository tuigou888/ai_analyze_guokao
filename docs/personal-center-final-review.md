### Important

**R1：同浏览器另一标签切换账号后，旧资料页可把 A 的表单写进 B 的账户。**

- 位置：`web/src/components/account/ProfileForm.vue:20`（写入先于 owner 校验）、`:10`（仅接收响应时校验）；关联 `web/src/auth.js:5`、`web/src/router/index.js:29` 和 `internal/serve/account.go:122`。
- 触发：同一个浏览器上下文有两个标签，A/B 两账号资料 revision 恰好相同（两个新账号都是 0 即满足）。标签一以 A 登录并打开资料表单；标签二退出 A 后登录 B。浏览器共享的 `gk_user` Cookie 此时属于 B，但标签一的 `auth.user`、profile 和 draft 仍属于 A。返回标签一点“保存资料与偏好”。
- 根因：`save()` 直接发送 A 的完整可编辑 draft；页面内存没有跨标签账号变更通知，也未在写请求中建立可由服务器原子校验的页面身份前提。服务端正确按当前 B Cookie 调用 `UpdateProfile`，相同的数字 revision 会通过 B 的 CAS，故 A 的昵称、简介、头像、目标和偏好被保存到 B。收到 B 的 Profile 后，`receive()` 才因用户名不匹配返回 null，这只能丢弃 ACK，不能阻止已经完成的数据库写入。第一标签还没有明确错误提示。
- 影响：普通多标签切换账号就可能污染另一个账户资料，违背换账号不得沿用其他人的偏好这一要求和正常用户对“当前显示账户”的保存预期。此处不是未经认证访问 B 的漏洞；问题是界面展示身份与浏览器实际 Cookie 身份不一致时发生错误账户写入。
- 证据：上述为实际代码调用链的静态确定性发现，本审查没有新启动浏览器，未将其标为动态复现。现有 `task4-ordering4-results.json` 覆盖同账号响应乱序，`task4-personal17-results.json` 最后两项覆盖同一页面换账号后的缓存/迟到 ACK；均未覆盖“另一标签换 Cookie 后，旧页面新发起 PUT”。已及时向根代理报告，建议以真实双标签最小用例先复现。
- 修复方向：保存前及服务器写入时拒绝页面预期身份与已验证 Cookie 身份不一致的操作，并通知/失效同浏览器其他标签的旧账户状态。预期身份只能作为拒绝写入的前置条件，查询用户仍必须完全来自已验证 Cookie；保持 ProfileUpdate 仅可编辑字段与 revision、PUT 路由和现有 Origin 合同。单纯在成功响应后丢弃、只比较页面内存 `auth.user` 或仅做非原子的 GET 预检不足以完整解决此类竞态。增加同一 browser context 两页、A/B 相同 revision 的回归，断言 B 资料未变，旧页明确提示重新进入；并保留现有同账号 CAS/乱序与单页换账号回归。

- `internal/serve/study.go:30` 先验证 Cookie，`:39` 在业务调用前执行身份前提；`internal/serve/identity.go:10` 仅将 Header 与已经验证的用户 ID 比较。缺省保持旧合同，非法格式 400、不匹配 409/account_changed，不把 Header 用作查询用户或授权来源。资料 DTO、PUT 合同、昵称/revision 事务均未扩展身份字段。

- `web/src/components/account/ProfileForm.vue:15`、`:22` 在已知账号变化时本地拒绝保存，`:23`、`:24` 同样保护重载和 CSV；账号变化的 409 不再冒充同账号资料 CAS 冲突。表单输入不会被自动重载、改绑新账号或重发。`auth.js:9` 的通知只设置失效标记、清缓存，不能授予新身份；仅退出通知的输入保留也有实际回归。
- `web/src/api.js:18`、`auth.js:15` 和 `router/index.js:38` 按发起 owner 隔离迟到错误/401；`Security.vue:7` 结合存活状态和 owner 检查成功回调，`App.vue:11` 在等待离开保护前捕获身份且在成功后复查。旧 A 改密、会话撤销、退出完成后，不会清除后来 B 的身份或继续读取 B 的会话。
