## 一、总体评价

该项目在**认证、鉴权、输入处理**上的工程质量明显高于同类自部署应用，多数常见漏洞品类已被有意设计规避。以下为实测确认**有效**的防护：

| 防护项 | 实测结果 |
| --- | --- |
| CSRF / 跨站提交 | 无 `Origin` → 403；`Origin: http://evil.com` → 403；`null` → 403；`127.0.0.1:18080.evil.com` → 403 |
| 会话 Cookie | `HttpOnly; Secure; SameSite=Strict`；用户 7 天、管理员 12 小时 |
| 身份互斥 | 管理端与用户端 Cookie 不能同浏览器并存；登其一吊销另一 |

| 路径穿越 | `/media/题目图/../../../etc/passwd`、`..%2f` 编码、符号链接逃逸 → 404；`/media/secret.txt` → 404；未登录 → 401 |

| SQL 注入 | 全部参数化；动态列名来自白名单 map；FTS 检索词 `"` 双写转义；`admin q` 用 `ESCAPE '\'` 转义 `%_\` |

## 二、发现的问题

### H-1【高危】认证限速退化为全站单一限速桶 → 低成本全站登录拒绝服务 ✅ 已修复

**位置**：`internal/serve/auth_limit.go`

**问题**：限速键由「客户端 IP」+「账号」组合，但有两个放大效应：

1. `entries` 是**进程级全局 map**，同一 IP 失败累计 30 次即封禁该 IP 键；`slots` 并发闸门**全局仅 2 个**；
2. `/api/auth/login`、`/api/auth/register`、`/api/admin/login`、`/api/auth/email-code` **共用同一份 IP 键**，一个打满其余三个一并 429。

**实测**：

```
连续 35 次错误登录 → 401 ×27, 429 ×8
限速期间换任意用户名（audituser2 / newuser_x）→ 全部 429
限速期间 /api/admin/login（正确口令）→ 429
限速期间 /api/auth/register → 429
限速期间 /api/auth/email-code → 429
并发槽：10 个并发合法登录 → 429 ×8, 401 ×1, 200 ×1
```

**影响**：未认证攻击者无需凭据，持续发错误登录即可让**全部用户与管理员在持续时间内无法登录**（约 60 秒窗口，可循环维持）；`email-code` 被封导致新用户无法注册；并发闸门 2 使正常高峰合法登录大面积失败。

**建议**：拆分桶（账号维度防撞库 / IP 维度防滥用，不互相放大）；`email-code`、`register`、`admin/login` 独立桶；仅对失败计数或成功后清零；并发闸门按接口独立或提高配额。

**修复（2026-11-17）**：

- 限速器重写为**按接口独立分桶**：`/api/auth/login`、`/api/auth/register`、`/api/admin/login`、`/api/auth/email-code` 各自拥有独立的账号桶、IP 桶与并发信号量（登录/注册/管理端登录各 8 槽，验证码 4 槽）。打满任一接口不再牵连其余接口。
- **账号桶与 IP 桶分开计数、不叠加**，避免互相放大；账号键与邮箱键均为 SHA-256 摘要，不落原始输入。
- **登录/注册/管理端登录只对失败计数**（401/400/403/部分 5xx），**成功即清零账号桶**——受害者被恶意锁定时，用正确口令一旦成功即可立即解除；IP 桶在成功时保留，防止用一次合法登录重置扫描预算。验证码发送仍按成功计数（每封邮件有真实成本）。
- 桶表设 8192 条上限并在满时拒绝新增键，防止海量伪造用户名冲刷掉正在生效的封禁。
- 回归测试：`TestAuthLimiterBucketsArePerEndpoint`（接口隔离）、`TestAuthLimiterSuccessClearsAccountFailures`（成功清零）、`TestAuthLimiterBoundsOneAccountAcrossIPs`（账号维度跨 IP 封禁）、`TestAuthLimiterIgnoresSpoofedForwardedHeaders`、`TestAuthLimiterSlotsOnlyGatePasswordEndpoints`。

### H-2【高危】容器/反代部署下客户端 IP 坍缩，全站共用一个限速桶（放大 H-1） ✅ 已修复

**位置**：`internal/serve/auth_limit.go`（`clientIP`）、`docker-compose.yml`、`cmd/gk/serve.go`

**问题**：`clientIP()` 仅在来源地址命中 `--trusted-proxies` 时才采信 `X-Forwarded-For`。两条部署路线的安全语义不一致：

- `docker-compose.yml` 的 `command` 只传 `--public-origin`，**没有** `--trusted-proxies`；
- `deploy/gk.service` **有** `--trusted-proxies 127.0.0.1/32,::1/128`。

容器路线下 `RemoteAddr` 恒为 Docker 网关，所有公网用户落到**同一个 IP 键**。

**实测**（容器 + 端口映射）：

```
从 127.0.0.1 登录   → 会话 ip_hint: 172.17.0.*
从 192.168.1.16 登录 → 会话 ip_hint: 172.17.0.*
```

**影响**：任一匿名访客触发 30 次失败即可锁死**全站所有用户**登录（H-1 放大为"一个请求瘫痪"）；会话列表 `ip_hint` 失去审计价值。

**建议**：compose `command` 增加 `--trusted-proxies 172.16.0.0/12`（或 `--public-origin` + 反代覆盖 `X-Forwarded-For` 并显式配可信网段）；把该验收项从 systemd 扩展到 Docker 路线；增加启动自检日志。

**修复（2026-11-17）**：

- `docker-compose.yml` 的 `command` 增加 `--trusted-proxies=${GK_TRUSTED_PROXIES:-172.16.0.0/12}`；`deploy/.env.example` 同步给出该变量及"不要填 `0.0.0.0/0`"的说明。容器的发布端口仍只绑定 `127.0.0.1`，宿主反代是唯一来源，信任 Docker 桥接网段是正确语义。
- `gk serve` 增加**启动自检**：配置了 `--public-origin` 但未设置 `--trusted-proxies`、且监听地址非回环时，向 stderr 明确告警"客户端 IP 将坍缩为代理地址"（`cmd/gk/serve.go`）。
- 两条部署路线现在等价：systemd `127.0.0.1/32,::1/128`、Docker `172.16.0.0/12`，并在 `docs/部署方案.md` 验收清单中一并覆盖。
- 回归测试沿用 `TestTrustedProxyUsesRightmostUntrustedHop`（右起第一个不可信跳），并验证伪造 `X-Forwarded-For` 不能绕过 IP 桶。

### M-1【中危】管理端设置接口无键白名单，可写入任意配置键 ✅ 已修复

**位置**：`internal/serve/server.go`（`handlePutSettings`）、`internal/setting/setting.go`

`handlePutSettings` 遍历客户端 `map[string]string` 不做键校验，`Store.Set` 同样不校验；`Store.All()` 遍历全表并**回显所有键**。

**实测**：

```
PUT /api/admin/settings {"totally.bogus.key":"injected"} → 200
DB: totally.bogus.key | injected | 0
GET /api/admin/settings → 该键出现在返回体
```

**影响**：仅 super 可调用，直接危害有限；但配置表被任意污染，未来若配置键用作逻辑开关会演变为逻辑绕过面。

**建议**：`handlePutSettings` 与 `Store.Set` 加入键白名单（`Defaults` ∪ 已知键），未知键 400；`All()` 只输出已知键。

**修复（2026-11-17）**：

- `internal/setting` 新增 `KnownKeys`（全部 16 个受支持键）与 `IsKnownKey`；`Store.Set` 对未知键返回 `ErrUnknownKey`，`Store.All()` 过滤掉库中已有的历史脏键。
- `handlePutSettings` 在写入前整批校验，出现未知键直接 `400 未知的配置键: xxx`，不落任何一条。
- 回归：`TestSettingsKeepSMTPPasswordWhenEmptyOrMasked` 通过；新增 `TestSettingsRejectUnknownKeys` 验证未知键整批 400、库中不落键、合法键不部分写入，且 `Store.Set` 层同样拒绝。

### M-2【中危】管理员可控 `base_url` + 错误原文回显 → 内网探测 / SSRF 面 ✅ 已修复

**位置**：`internal/serve/server.go`（`handlePutSettings` / `handleTestLLM`）、`internal/serve/email_code.go`（`handleTestMail`）、`internal/netguard`

super 可任意改 `llm.base_url` / `mail.smtp_host` 并触发 `POST /api/admin/test-llm`、`/api/admin/test-mail`，服务端向该地址发起真实请求，且**把底层错误原文透传**。

**实测**：

```
PUT settings {"llm.base_url":"http://127.0.0.1:18080"} → 200
POST /api/admin/test-llm → 502
{"error":"LLM 调用失败（可重试）: Post \"http://127.0.0.1:18080/chat/completions\": dial tcp 127.0.0.1:18080: connect: connection refused"}
```

**影响**：仅 super 权限下成立。但一旦管理员凭据泄露，该接口可直接做**内网资产探测**：通过错误文案区分"端口开放但非 HTTP"（EOF/超时）与"连接被拒"，构成有效扫描原语；同时泄露内部主机名/网段/拓扑。

**建议**：对 `base_url` / `smtp_host` 校验目标，禁止回环、链路本地、RFC1918（除非显式允许）；错误响应只返回分类化文案，原文仅写服务端日志。

**修复（2026-11-17）**：新增 `internal/netguard` 包，做两道防线。

- **保存时校验**：`handlePutSettings` 对 `llm.base_url`（必须 http/https、无 userinfo、主机非内网）与 `mail.smtp_host` 校验；命中回环、RFC1918、链路本地（含 `169.254.169.254` 云元数据）、CGNAT、组播、ULA 等返回 400。
- **建连时复核**：`netguard.Dialer` 作为 `net.Dialer.Control` 在**解析后的 IP** 上再判一次，挡住"域名解析到内网"与 DNS 重绑定；`test-llm` 的自定义 Transport 与 `mail.Send` 的可选拨号函数都走这条路径。
- **错误分类化**：`test-llm` / `test-mail` 不再回显 `dial tcp ...: connection refused` 之类的原文（原文只写 `slog`），响应仅给"无法连接网关 / HTTP 状态码 / 超时 / 已拒绝内网目标"等分类文案。
- 自部署常把 LLM/SMTP 放在内网，新增 `gk serve --allow-private-outbound` 显式放行；默认拒绝。
- 回归：`internal/netguard/netguard_test.go`（网段判定、URL/主机校验、拨号守卫）。

### M-3【中危】缺少 CSP / HSTS / Permissions-Policy 纵深防御 ✅ 已修复

**位置**：`internal/serve/origin.go`、`deploy/nginx.d/gk.conf.example`

已设 `X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`、`X-Frame-Options: DENY`；**缺** `Content-Security-Policy`、`Strict-Transport-Security`、`Permissions-Policy`（Nikto 三项 [013587] 命中）。

**风险点**：前端存在 `v-html` 汇聚点 `web/src/components/RichText.vue:26`。审阅确认当前实现**安全**：文本先 `escape()`，图片路径走 `题目图/公式图` 白名单 + 正则 + `encodeURIComponent`，KaTeX `trust:false, throwOnError:true`。故当前**无可利用 XSS**；但缺 CSP 意味着未来新增渲染点或升级 KaTeX 引入 `\href`/`\htmlData` 时无兜底。

**建议**：`sameOrigin` 统一下发 CSP（`default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'none'`，注意前端有内联 `style=`）；HSTS 在反代层 `add_header ... always`；补 `Permissions-Policy: geolocation=(), microphone=(), camera=()`。

**修复（2026-11-17）**：

- `sameOrigin` 对所有响应统一下发 CSP（含 `frame-ancestors 'none'`、`base-uri 'none'`、`form-action 'self'`；`style-src` 保留 `'unsafe-inline'` 以兼容 Vue 内联 style 与 KaTeX）与 `Permissions-Policy`。
- **HSTS 仅在 HTTPS 请求上下发**（直连 TLS 或可信代理 + `X-Forwarded-Proto: https`），避免把只走明文 HTTP 的内网部署锁死；生产环境由反代再冗余 `always` 一份。
- `deploy/nginx.d/gk.conf.example` 的 TLS server 块补齐完整 `add_header ... always` 列表（含 HSTS），因为 nginx 的 `add_header` 会覆盖就地继承值，必须列全。
- 回归：`TestSecurityHeadersAlwaysEmitted` 验证三种头均存在、明文请求不带 HSTS。
