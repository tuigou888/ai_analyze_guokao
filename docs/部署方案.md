# 部署方案

本文给出行测研习的完整部署方案：先做现状分析，再对比两条可选路线，最后给出可直接执行的步骤、验收清单、备份与回滚流程，以及 Docker 路线当前必须修复的问题清单。

> 2026-10-16 复核更新：数据库 schema 现为 v13（注册邮箱验证码）；Docker 阻塞项已全部修复（§5 保留问题档案与新的使用流程）；新增「配置 SMTP」为注册前置步骤（A4.5）。

配套材料：

- 逐条命令的运维手册（宝塔路径）：[deployment-2c4g.md](deployment-2c4g.md)
- 接口与认证口径：[api-design.md](api-design.md)

## 0. 结论速览

1. **生产推荐路线 A：单机 systemd + Nginx（或 Caddy）反向代理。** 仓库已有完整产物（`deploy/gk.service`、`deploy/nginx.d/gk.conf.example`、`deploy/Caddyfile`、`deploy/backup.sh`），并有配套手册，风险最低。
2. **路线 B（Docker Compose）已在仓库修复，可直接使用。** `docker compose up -d --build` 构建并启动；备份独立成 profile，用 `docker compose run --rm backup` 触发。原 8 项阻塞问题的档案与修复记录见 [§5](#5-路线-bdocker-路线问题档案与修复记录)。
3. **两条路线都必须在部署前准备好三样东西**：含管理员的数据库一致性快照、与之配对的 `secret.key`、`data/90-图片/`。缺少管理员时 `gk serve` 会主动退出（`cmd/gk/serve.go:66`），容器会表现为“反复重启”。
4. **注册已改为邮箱验证码（schema v13）。** 部署后必须先由管理员在「设置 → 邮件服务」配置 SMTP 并通过测试邮件，否则用户收不到验证码、无法注册（未配置时验证码只打印服务端日志）。步骤见 A4.5。
5. **HTTPS 不是可选项。** 登录 Cookie 恒带 `Secure`（`internal/serve/server.go:141`、`internal/serve/study.go:229`），HTTP 下登录态无法保存；同时非 GET 请求有同源校验，代理必须正确传递来源信息，否则登录、答题、交卷等全部 POST 会返回 403。

## 1. 现状分析

### 1.1 运行架构

```
浏览器 --HTTPS--> Nginx/Caddy（反代 + 证书）
                      --HTTP 127.0.0.1--> gk serve（Go，单二进制，内嵌 Vue3 前端）
                                            ├─ SQLite（WAL，纯 Go 驱动）
                                            └─ <DataDir>/90-图片/{题目图,公式图}
```

关键事实：

- **单二进制交付。** Go 通过 `go:embed` 把前端产物、KaTeX 与字体一起打进二进制（`cmd/gk/assets.go`，前端输出目录配置在 `web/vite.config.js` 的 `outDir: '../cmd/gk/web_dist'`）。生产服务器不需要 Node.js。
- **单机 SQLite，不具备横向扩容能力。** 数据在同一个 `gk.sqlite` 内；补一台机器无法直接分摊写入。容量规划按单机做。
- **`/admin` 与用户站点共用同一个端口**，通过路径区分，不存在独立的“管理端口”。任何把 8080/8081 当作“管理口”的设计都是误解。

### 1.2 运行依赖与端口

| 项目 | 值 | 说明 |
| --- | --- | --- |
| Go 版本 | 1.26.8+ | 见根目录 `go.mod` |
| 服务端依赖 | Chi + `modernc.org/sqlite` | 纯 Go，无 CGO，静态链接 |
| 前端 | Vue 3 + Vite + KaTeX | 仅在构建期需要 Node 24 LTS |
| 生产监听端口 | `8080`（模板中为 `127.0.0.1:8080`） | 由 `deploy/gk.service` 固定 |
| 本地开发端口 | `8081` | `make serve`，勿与生产 8080 混用 |
| Vite 端口 | `5173` | 仅开发期 |
| 健康检查 | `GET /healthz` → `{"ok":true}` | `internal/serve/server.go:56` |

**环境变量只有一个是被程序读取的**：`GK_SECRET_KEY`（`internal/setting/setting.go:101`）。`--addr`、`--trusted-proxies`、`--public-origin`、`--db`、`--data`、`--secret-key-file` **只能通过命令行 flag 传入**，不读环境变量。Go 运行时自带的 `GOMAXPROCS`、`GOMEMLIMIT` 是有效的（由 Go runtime 解析），但 `GK_ADDR`、`GK_TRUSTED_PROXIES` 之类自定义名不会被识别——这正是 Docker 路线出问题的根因之一。

### 1.3 数据资产与实测体量（本机）

| 路径 | 体量 | 是否随部署包分发 | 备份要求 |
| --- | --- | --- | --- |

题库规模：27,449 道去重题，58,890 次题目出现，约 550 道已有标注。

### 1.5 部署必须满足的安全约束

这些约束来自代码，部署时不能绕过：

1. **Cookie 恒为 `Secure` + `HttpOnly` + `SameSite=Strict`** → 对外必须 HTTPS，否则登录后立刻掉线。
2. **非 GET 请求的同源校验**（`internal/serve/origin.go:32-54`）：默认期望值由请求的 scheme + Host 推出。反代场景下，若 Go 看不到 `X-Forwarded-Proto: https`，或该来源 IP 不在 `--trusted-proxies` 白名单内，期望值会退化成 `http://<域名>`，与浏览器发来的 `https://<域名>` 不匹配 → **所有 POST 403**。两种正确做法：给反代配置 `--trusted-proxies` 并透传 `X-Forwarded-Proto`，或直接用 `--public-origin https://你的域名` 固定期望值（更简单、更稳）。
3. **`/media/*` 需要登录**（`internal/serve/server.go:85`），且只暴露 `<DataDir>/90-图片/{题目图,公式图}/` 下的图片文件（`internal/serve/media.go`）。因此 `--data` 必须指向**包含 `90-图片` 目录**的那一层，图片目录不要挂到 Web 静态根。
4. **`8080` 不得对公网开放**，只允许本机/容器网络访问。
5. **`--data` 与数据库路径要在启动参数中对齐**；镜像/容器里挂载的卷路径必须与参数一致。

## 2. 路线选择

| 维度 | 路线 A：systemd + Nginx/Caddy | 路线 B：Docker Compose |
| --- | --- | --- |
| 现状 | 文档与产物齐全，可直接执行 | 已修复，`docker compose up -d --build` 可用 |
| 交付方式 | 目录安装 `/opt/gk`，systemd 托管 | 镜像 + 卷挂载 |
| HTTPS | Nginx/Caddy 在宿主机 | 需额外反代或证书方案 |
| 资源隔离 | systemd 限额（MemoryMax/CPUQuota/沙箱） | cgroup 限额 |
| 备份 | `gk-backup.timer` | `docker compose run --rm backup`（独立 profile） |
| 升级 | 换二进制 + 重启 | 重建镜像 + 重启 |
| 回滚粒度 | 二进制 + 数据库快照 | 镜像 tag + 数据库快照 |
| 推荐度 | ★★★★★ 生产首选 | ★★★★ 修复后可用，建议目标机实测 |

**结论**：把路线 A 作为上线主路径；路线 B 作为可选容器化形态，先按 §5 修复再评估。

## 3. 路线 A 详细步骤（推荐）

### A0. 前置条件核对

- [ ] 服务器：2 核 4GB 及以上，Ubuntu/Debian LTS，磁盘留出 ≥5 GB 给数据库、图片、备份与日志。
- [ ] 已准备：含管理员的 `gk.sqlite` 快照、配对的 `secret.key`、`data/90-图片/`。
- [ ] 中国大陆地域 + 域名对外：**先完成 ICP 备案**。
- [ ] 本地具备 Go 1.26.8+、Node 24 LTS、make、tar。
- [ ] 决定 Origin 策略：推荐 `--public-origin https://你的域名`（见 A6）。

### A1. 本地构建与打包

```bash
# 1) 前端 + 二进制 + 部署包（约 12 MB）
make release                 # 产出 var/gk-linux-amd64.tar.gz

# 2) 数据库一致性快照（不要直接拷贝正在使用的 .sqlite）
go build -buildvcs=false -o var/gk ./cmd/gk
./var/gk backup --db var/db/gk.sqlite --bundle var/deploy-backup
./var/gk backup --verify-bundle var/deploy-backup

# 3) 图片包
tar -czf var/gk-images.tar.gz -C data 90-图片

# 4) 记录校验和，便于服务器端比对
sha256sum var/gk-linux-amd64.tar.gz var/gk-images.tar.gz var/deploy-backup/gk.sqlite
```

打包与传输的注意事项：

- `var/gk-linux-amd64.tar.gz` **不含**数据库、密钥、图片，需按上面单独准备。
- `var/deploy-backup/` 内应含 `gk.sqlite`、`secret.key`、`complete.json`；无完成标记的目录禁止用于恢复。
- 目标为 ARM64 时，把 `make release` 里的 amd64 构建替换为 `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -buildvcs=false -trimpath -o var/release/gk ./cmd/gk` 后自行打包。
- **密钥与数据库必须同一批次**，不要混用。`secret.key` 不进 Git、不进发布包、不贴到聊天记录。

上传（示例账号 `ubuntu`，SSH 22）：

```bash
scp var/gk-linux-amd64.tar.gz ubuntu@SERVER_IP:/tmp/
scp var/deploy-backup/gk.sqlite ubuntu@SERVER_IP:/tmp/deploy-gk.sqlite
scp var/deploy-backup/secret.key ubuntu@SERVER_IP:/tmp/gk-secret.key
scp var/gk-images.tar.gz ubuntu@SERVER_IP:/tmp/
```

### A2. 服务器准备

腾讯云防火墙（公网入站）与操作系统防火墙是两套规则，都要配置：

| 端口 | 用途 | 来源 |
| --- | --- | --- |
| 22/TCP（实际 SSH 端口） | SSH 与上传 | 仅自己的固定 IP |
| 80/TCP | HTTPS 跳转与证书验证 | `0.0.0.0/0` |
| 443/TCP | HTTPS 站点 | `0.0.0.0/0` |
| 8080/TCP | Go 服务 | **不开放**，仅本机回环 |
| 宝塔面板端口 | 面板 | 仅自己的固定 IP |

```bash
# 服务账号与目录（root 或 sudo）
sudo useradd --system --home-dir /opt/gk --shell /usr/sbin/nologin gk
sudo install -d -o root -g root -m 755 /opt/gk
sudo install -d -o gk -g gk -m 700 /opt/gk/var
sudo install -d -o gk -g gk -m 700 /opt/gk/var/db /opt/gk/var/runs /opt/gk/var/logs /opt/gk/var/backups
sudo install -d -o root -g root -m 755 /opt/gk/data
```

时区固定为 Asia/Shanghai（systemd 单元未显式设置 TZ，靠系统时区；如需可加 `Environment=TZ=Asia/Shanghai`）。

### A3. 安装程序与数据

```bash
# 程序包
sudo tar -xzf /tmp/gk-linux-amd64.tar.gz -C /opt/gk
sudo chmod 755 /opt/gk/gk

# 图片
sudo tar -xzf /tmp/gk-images.tar.gz -C /opt/gk/data
sudo chown -R root:gk /opt/gk/data
sudo find /opt/gk/data -type d -exec chmod 755 {} +
sudo find /opt/gk/data -type f -exec chmod 644 {} +
# 期望存在：/opt/gk/data/90-图片/题目图/ 与 /opt/gk/data/90-图片/公式图/

# 数据库与密钥（0600，属主 gk）
sudo install -o gk -g gk -m 600 /tmp/deploy-gk.sqlite /opt/gk/var/db/gk.sqlite
sudo install -o gk -g gk -m 600 /tmp/gk-secret.key  /opt/gk/var/secret.key

# 清理临时明文
rm -f /tmp/gk-linux-amd64.tar.gz /tmp/gk-images.tar.gz /tmp/deploy-gk.sqlite /tmp/gk-secret.key
```

首次启动会自动执行到 v13 的追加迁移（v13 为注册邮箱绑定与邮件验证码表；存量账号邮箱为空串，不受影响）、建中文 FTS5 索引并刷新考点映射，这一步会明显慢于后续启动，**期间不要杀进程**。上线库必须从含题库的快照开始，不要用空库覆盖。

### A4. 管理员账号

```bash
cd /opt/gk
# 快照已含管理员：跳过，直接用已知账号登录
# 需要新建（交互输入口令）：
sudo -u gk ./gk admin create --db /opt/gk/var/db/gk.sqlite --user admin
# 遗失口令则重置（会注销旧会话）：
sudo -u gk ./gk admin passwd --db /opt/gk/var/db/gk.sqlite --user admin
```

启动前自查：`gk` 用户能写 `/opt/gk/var`，能读 `/opt/gk/gk`、`taxonomy/`、`data/90-图片/`。不要放开整个 `/opt/gk` 的写权限。

### A4.5 配置 SMTP（注册功能的上线前置）

注册新用户需要邮箱验证码，服务端通过管理员设置里的 SMTP 发信：

1. 浏览器打开 `https://你的域名/admin/login` 登录管理员。
2. 进入「设置」，找到「邮件服务（注册验证码）」卡片，填写 SMTP 主机、端口、用户名、密码、发件人后点卡片内「保存」。QQ 邮箱示例：`smtp.qq.com` / `465` / 用户名=完整邮箱 / 密码=**SMTP 授权码**（非登录密码）；465 走隐式 TLS，其他端口自动 STARTTLS，需认证而链路无法加密时会拒绝发送。
3. 用「发送测试邮件」填入收件人发送，确认邮件到达（含垃圾箱）。
4. 未配置时走开发降级：验证码只打印在 `sudo journalctl -u gk` 日志里（搜索「开发降级」）；发送失败时注册页提示「验证码发送失败，请稍后重试」。**开放注册前必须完成本步。**
5. 服务器需能出网访问 SMTP 端口（465/587）；腾讯云轻量默认放通出站，如自建出站策略需放行。

### A5. 启动 systemd 服务

```bash
sudo cp /opt/gk/deploy/gk.service /etc/systemd/system/gk.service
sudo systemctl daemon-reload
sudo systemctl enable --now gk
sudo systemctl status gk --no-pager

sudo ss -lntp | grep ':8080'                 # 应为 127.0.0.1:8080
curl --fail http://127.0.0.1:8080/healthz    # {"ok":true}
sudo journalctl -u gk -n 100 --no-pager      # 排障
```

`deploy/gk.service` 已含的关键约束：`MemoryHigh=900M`/`MemoryMax=1200M`/`CPUQuota=150%`、`ProtectSystem=strict` + `ReadWritePaths=/opt/gk/var`、`UMask=0077`、`NoNewPrivileges=true`。这些是按 2 核 4GB 与系统共存留出的余量，不要为“提速”而放大。

### A6. 反向代理与 HTTPS

**这一步决定 POST 是否可用**，务必按下面取舍：

方案一（推荐，简单）：在 `ExecStart` 增加 `--public-origin https://你的域名`。这样同源校验使用固定值，不依赖转发头可信度。

方案二：信任本机回环代理并透传协议头。`deploy/gk.service` 已配 `--trusted-proxies 127.0.0.1/32,::1/128`，把 Nginx 配成从回环访问即可，并在代理配置中确保：

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-For $remote_addr;   # 覆盖客户端传入值，不要透传
proxy_set_header Host $http_host;
```

Nginx 侧（`deploy/nginx.d/gk.conf.example` 已含）：

```bash
sudo cp /opt/gk/deploy/nginx.d/gk.conf.example /etc/nginx/conf.d/你的域名.conf
# 替换 practice.example.com、证书路径，然后：
sudo nginx -t && sudo systemctl reload nginx
```

关键点：

- `location /` 反代到 `http://127.0.0.1:8080`；静态资源可加长缓存，但**图片走 `/media/` 需登录，不要绕开 Go 服务直挂静态目录**。
- 强制 HTTPS 放在证书签发成功之后；先有 80 与验证路径，再开跳转。
- 登录限流在 Go 侧按 TCP 来源计算，反代后所有用户共用同一限流（当前版本默认每分钟 30 次量级），低流量够用；如遇共享限流再调整。

Caddy 备选：改 `deploy/Caddyfile` 的域名后 `caddy run`，自动申请证书并反代 `127.0.0.1:8080`。**不要同时启用 Nginx 与 Caddy。**

### A7. 上线验收清单

- [ ] `https://域名/healthz` 返回 `{"ok":true}`。
- [ ] A4.5 的 SMTP 配置已保存，「发送测试邮件」可正常收到。
- [ ] `/login` 用真实邮箱注册（收码 → 输入验证码 → 登录）；`Set-Cookie` 带 `HttpOnly`、`Secure`、`SameSite`。
- [ ] `/questions` 可筛选模块/年份/地区/考试类型，中文关键词可搜题干。
- [ ] 开始练习 → 答题 → 刷新后草稿可恢复 → 交卷看到判分与解析。
- [ ] 多选、判断题、陕西 A–H 选项题正常；无答案题不可练习。
- [ ] 错题进 `/wrongbook`，重做正确后标记已订正；`/papers`、`/concepts`、`/records` 正常。
- [ ] 解析公式（KaTeX）与题图/公式图显示正常；手机端无横向溢出。
- [ ] 未作答时请求 `/api/questions/:id/reveal` 返回 403；提交非空答案后才可读解析。
- [ ] 普通用户无法进入管理员功能；管理员仅从 `/admin/login` 登录。
- [ ] 关闭公网 8080 规则后，站点仍可通过 443 访问。

### A8. 每日备份

```bash
sudo cp /opt/gk/deploy/gk-backup.service /etc/systemd/system/
sudo cp /opt/gk/deploy/gk-backup.timer   /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now gk-backup.timer
sudo systemctl start gk-backup.service
sudo systemctl list-timers gk-backup.timer
```

- 备份落在 `var/backups/<UTC时间>/`，含 `gk.sqlite`、实际生效的 `secret.key`、`complete.json`。
- 脚本**不自动清理旧快照**，需自行制定保留策略；磁盘写满会导致数据库无法写入。
- 若使用 `GK_SECRET_KEY`，把它放在 `gk:gk`、0600 的 `/opt/gk/var/gk.env`，并让网站与备份服务读同一份；宝塔计划任务不继承 systemd 环境，建议统一用 `systemctl start gk-backup.service` 触发。
- 定期把关键快照复制到另一台机器——本地快照扛不住磁盘损坏。

### A9. 升级与回滚

升级：

```bash
# 1) 本地 make release，上传新包
# 2) 先触发一次备份
sudo systemctl start gk-backup.service
# 3) 停服务并留存旧二进制
sudo systemctl stop gk
sudo cp /opt/gk/gk /opt/gk/var/gk.previous
# 4) 解压新包（只覆盖程序，不动 var/db、secret.key、data/）
sudo tar -xzf /tmp/gk-linux-amd64.tar.gz -C /opt/gk
sudo chmod 755 /opt/gk/gk
sudo systemctl start gk
sudo journalctl -u gk -n 50 --no-pager
```

要点：

- 前端随二进制更新，发布后必须让浏览器刷新，避免新旧页面混用。
- 草稿保存/交卷请求需带 `draft_revision`，前后端要同时升级；并发冲突返回 409，不要用旧答案自动重试覆盖。
- 密钥不存在但库里已有加密配置时会拒绝启动，必须恢复匹配密钥。

回滚：**如果新版本已执行数据库 schema 迁移，回滚必须同时恢复升级前的 SQLite 快照（含匹配密钥）与旧二进制**，不能只换回旧程序配新 schema。恢复前先停服务，避免新旧 WAL/SHM 混合；完整恢复会回滚会话与密码状态，按恢复策略统一撤销历史会话并要求重新登录。

## 4. 灾备与恢复要点

1. 在异机/隔离环境先验证：`./gk backup --verify-bundle <备份目录>`，通过后再恢复。
2. 不要在备份目录原地恢复或启动服务，复制到新的恢复路径。
3. 恢复环境若设置了 `GK_SECRET_KEY`，需删除该覆盖或改成与备份密钥一致，否则会覆盖文件密钥导致解密失败。
4. 停服务 → 保留当前 `gk.sqlite`/`-wal`/`-shm` 作为回滚副本 → 安装已确认的快照与配对密钥 → 启动 → 查 `/healthz`。
5. 图片批次文件与 `var/runs/<批次>/bucket_owner.json` 需单独备份，不随数据库快照走。

## 5. 路线 B：Docker 路线问题档案与修复记录

### 5.1 实测发现的问题（修复前档案）

> 修复状态（2026-10-16）：以下问题（含原 7 项之外新增发现的第 8 项）已在仓库全部修复，`docker-compose.yml` 已重写并可用。本节表格保留为问题档案。

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | `docker-compose.yml` 变量插值缺右花括号 | `docker compose config` 报 `invalid interpolation format`，指向 `GK_TRUSTED_PROXIES=${GK_TRUSTED_PROXIES:-127.0.0.1/32,...` | **compose 直接无法解析，任何服务都起不来** |
| 2 | compose 引用的 `docker-entrypoint.sh` 不存在 | `docker-compose.yml:42` `entrypoint: ["/opt/gk/docker-entrypoint.sh"]`；仓库内 `find -name docker-entrypoint*` 无结果，Dockerfile 也未 COPY | `backup` 服务启动即失败；`docker-run.sh` 的备份路径无法使用 |
| 3 | `GK_ADDR` 不被程序读取，容器实际绑定 `127.0.0.1:8080` | 唯一读取的环境变量是 `GK_SECRET_KEY`（`internal/setting/setting.go:101`）；`serve` 的 `--addr` 默认 `127.0.0.1:8080`（`cmd/gk/serve.go:29`），Dockerfile `CMD ["serve"]` 未传 `--addr` | **健康检查（容器内 localhost）通过，但宿主机端口发布连不上**，表现为“容器 healthy 却打不开” |
| 4 | 图片卷路径与 `--data` 默认值不一致 | `docker-compose.yml:10` 挂载 `./var/data:/opt/gk/var/data`；`serve` 的 `--data` 默认 `data`，工作目录 `/opt/gk` → 实际读 `/opt/gk/data` | **所有题图/公式图 404**（`internal/serve/media.go:24`） |
| 5 | `GK_TRUSTED_PROXIES`/`GK_PUBLIC_ORIGIN` 不被读取 | 同 3，程序不读这两个变量 | 容器前置反代时同源校验失败，**登录/答题/交卷等 POST 全部 403** |
| 6 | 映射 `8081` 端口无意义 | `docker-compose.yml:16` `8081:8081`；程序无独立管理端口 | 无害但误导，应删除 |
| 7 | 镜像自带空数据库时无法启动 | `serve` 在管理员数为 0 时返回错误（`cmd/gk/serve.go:66`） | 首次部署若不预置含管理员的库，容器反复重启 |
| 8 | compose 无 `build` 段 | 服务只声明 `image`，`docker compose up --build` 与 `docker-run.sh build` 都不会产出镜像 | 首次部署无镜像可用（拉取失败），构建流程实际缺失 |

> 说明：`GOMAXPROCS`、`GOMEMLIMIT` 是 Go runtime 原生变量，这两项在 compose 中是有效的；问题只出在 `GK_*` 自定义变量上。

### 5.2 修复记录（已落地）

1. **修语法**：补全 `${GK_TRUSTED_PROXIES:-...}` 的 `}` 与引号（若按第 5 条直接删除该变量则一并消失）。
2. **显式传参**：把 `CMD ["serve"]` 改为带全部 flag 的形态，或在 compose 用 `command:` 覆盖：

   ```yaml
   command:
     - serve
     - --db=/opt/gk/var/db/gk.sqlite
     - --data=/opt/gk/var/data
     - --secret-key-file=/opt/gk/var/secret.key
     - --addr=0.0.0.0:8080
     - --public-origin=https://${DOMAIN}
   ```

   用 `--public-origin` 可一次性解决第 5 条，且不需要信任转发头。
3. **对齐图片路径**：要么保持 `--data=/opt/gk/data` 并把卷挂成 `./var/data:/opt/gk/data`，要么保持卷路径并把 `--data` 指向 `/opt/gk/var/data`。二选一，别混。
4. **补 entrypoint 或改命令**：最简单是不引入脚本，让 `backup` 服务直接用 `gk backup`；注意 compose 不会做 shell 展开，需要显式 shell：

   ```yaml
   backup:
     image: ${IMAGE_NAME:-practice-gk}:${IMAGE_TAG:-latest}
     entrypoint: ["/bin/sh", "-c"]
     command:
       - >-
         exec /opt/gk/gk backup
         --db /opt/gk/var/db/gk.sqlite
         --secret-key-file /opt/gk/var/secret.key
         --bundle /opt/gk/var/backups/gk-$$(date +%Y%m%d-%H%M%S)
   ```

5. **删除无意义的 `8081:8081` 映射**，改为在文件顶部统一维护 `DOMAIN`。
6. **预置数据**：镜像不含数据库/密钥/图片。首次启动前在宿主机备好 `./var/db/gk.sqlite`（含管理员）、`./var/secret.key`、`./var/data/90-图片/`；或用一次性容器创建管理员：

   ```bash
   docker compose run --rm gk admin create --db /opt/gk/var/db/gk.sqlite --user admin
   ```

7. **反代与证书**：容器方案仍需在宿主机（或独立容器）放 Nginx/Caddy 终止 TLS，并反代到 `127.0.0.1:8080`；`--public-origin` 必须与实际访问域名一致。

以上已全部落在仓库的 `docker-compose.yml`（含新增 `build` 段）。备份服务改为 `profiles: ["backup"]`：默认 `up` 不再启动一次性备份容器，避免 `--wait` 启动时报错、也避免每次重启都生成全量备份；按需用 `docker compose run --rm backup` 触发。`--public-origin` 由 `.env` 的 `DOMAIN` 生成，缺失时 compose 直接报错而不是带病启动。

### 5.3 修复后的部署流程（目标形态）

```bash
# 宿主机准备数据
mkdir -p var/db var/data var/logs var/backups
cp /path/to/gk.sqlite     var/db/gk.sqlite     # 含管理员的快照
cp /path/to/secret.key    var/secret.key && chmod 600 var/secret.key
tar -xzf gk-images.tar.gz -C var/data          # 得到 var/data/90-图片/...

cp deploy/.env.example .env                    # 填 DOMAIN（如 gk.951357.xyz）
docker compose build                           # 构建镜像（本地构建，不走镜像仓库）

# 若库为空（还没有管理员），先创建管理员再启动：
docker compose run --rm gk admin create --db /opt/gk/var/db/gk.sqlite --user admin -password '强密码'

docker compose up -d
curl -f http://127.0.0.1:8080/healthz          # 期望 {"ok":true}
# 宿主机配置 Nginx/Caddy 反代 127.0.0.1:8080 并签发证书

# 每日备份（cron 示例，按需）：
# 0 3 * * * cd /path/to/repo && docker compose run --rm backup
```

说明：

- `--public-origin` 由 `.env` 的 `DOMAIN` 生成；缺失时 `docker compose` 会直接报错提示，不会带病启动。
- 宿主机发布端口由 `.env` 的 `GK_HOST_PORT` 控制（默认 8080），且只绑定 `127.0.0.1`：改端口（如 12001）后把反代目标同步改成 `http://127.0.0.1:12001`，公网防火墙不需要放行该端口。
- 备份快照落在 `var/backups/gk-<时间戳>/`；备份容器默认不随 `up` 启动，用 `docker compose run --rm backup` 按需或定时触发。
- 验收仍按 §A7 清单逐项执行；上线后同样先在 `/admin` 配置 SMTP 并通过测试邮件（见 A4.5），否则注册不可用。
